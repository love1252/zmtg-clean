# V0.7 真实渠道小范围灰度前置确认与执行方案

任务编号：V0.7-REAL-CHANNEL-GRAY-PREFLIGHT-PLAN-04A
日期：2026-07-07 CST +0800
任务类型：docs-only / 灰度前置规划 / 不开发功能

## 1. 文档目的

本文档用于在 V0.7 目标 4「真实渠道小范围灰度」启动开发前，统一真实渠道接入的前置判断、风险边界、验收口径和任务拆分。

本任务只做规划，不开发代码，不新增 API，不新增 UI，不修改 schema / migration，不读取或写入真实渠道 secret / API key，不做真实发送或真实出网测试。

目标 4 不是自动营销系统，也不是生产级真实渠道全面上线。目标 4 只能验证一条被严格 gated 的真实渠道小范围灰度链路。

## 2. 当前 V0.7 状态摘要

截至 V0.7 目标 3 完成后，当前随访链路已经具备以下基础：

- 目标 1：随访路径、随访任务和人工处理链路已形成基础闭环。
- 目标 2：消息草稿与人工确认链路已具备低敏展示和状态流转。
- 目标 3：触达安全治理与渠道灰度前置已完成，默认关闭、灰度前置、`sandbox` / mock only、no real send 已成为当前安全基线。

当前已完成的能力只允许生成受控记录、低敏 timeline、audit、dashboard 统计和页面说明，不代表已经具备真实企业微信或短信生产发送能力。

## 3. 目标 4 的定位

目标 4 的定位是「真实渠道小范围灰度 proof」，不是「真实渠道全面接入」。

目标 4 只允许在一个明确的测试边界内验证：

- 单租户。
- 单机构。
- 单测试客户。
- 单测试员工。
- 单条消息。
- 单个真实渠道。
- 人工确认后才允许触发。
- 可随时回滚到 `external_disabled`。
- 全程有 `MessageDelivery`、timeline、audit、dashboard 低敏记录。

目标 4 完成后，也只能说明「真实渠道小范围灰度 proof 已通过」，不能宣称生产级真实触达能力已经上线。

## 4. 为什么不能直接接真实渠道

真实渠道一旦接入，就会从内部模拟记录变成客户可见触达，风险级别明显上升。

不能直接接真实渠道的原因包括：

- 误发会直接影响客户，无法像 mock 记录一样只在内部回滚。
- 短信和企业微信都涉及客户授权、退订、触达频率和内容合规。
- 医美随访内容可能被客户理解为医疗建议，必须避免 AI 自动生成后直接发送。
- 真实渠道通常需要 secret、签名、模板、测试账号、回调配置和运营授权，不能在未建立治理边界前接入。
- 当前目标 3 的默认策略是外部渠道关闭，目标 4 必须以此为基线逐步打开一个最小口。

因此，真实渠道必须后置于触达安全治理、人工确认、灰度开关、审计、回滚、低敏展示之后。

## 5. 企业微信与短信的第一灰度渠道对比

| 对比项 | 企业微信测试通道 / 测试账号 | 短信测试通道 / 测试手机号 |
| --- | --- | --- |
| 误发影响 | 可先限定测试员工和测试客户，影响面相对更容易收敛 | 直接到达手机号，误发风险更高 |
| 成本风险 | 通常适合先做链路验证，成本风险较低 | 存在短信成本，批量误发影响更明显 |
| 合规约束 | 仍需 consent、opt-out、频控和人工确认 | 还需要签名、模板、退订、号码合规等更多约束 |
| 状态回写 | 适合先验证发送请求、失败、回写和人工确认闭环 | 状态回执依赖供应商，复杂度更高 |
| 第一阶段适配性 | 更适合第一灰度渠道 | 应后置，除非已有可靠测试短信通道和测试手机号 |

推荐优先顺序：

1. 优先企业微信测试通道或企业微信测试账号。
2. 短信放在后面。
3. 只有在已有可靠测试短信通道、测试手机号、签名模板、退订策略和成本控制时，才允许考虑短信作为灰度候选。

## 6. 推荐第一灰度策略

第一阶段只选择一个渠道，不允许企业微信和短信同时真实接入。

推荐第一灰度策略：

- 第一选择：企业微信测试通道或企业微信测试账号。
- 第二选择：短信测试通道和测试手机号。
- 默认所有外部渠道仍关闭。
- 未进入灰度的 tenant、institution、customer、employee、message 一律不触达。
- 所有非灰度渠道继续返回 `external_disabled`。

推荐企业微信测试通道优先的原因：

- 短信误发风险更高。
- 短信成本与合规风险更明显。
- 短信退订与签名模板限制更多。
- 企业微信测试账号更适合先验证状态回写、人工确认链路和灰度开关。

## 7. 灰度前置条件清单

进入真实渠道开发前，必须同时满足以下条件：

- 已明确唯一第一灰度渠道。
- 已明确单租户 `allowlist`。
- 已明确单机构 `allowlist`。
- 已明确单测试客户。
- 已明确单测试员工。
- 已明确单条测试消息。
- 已有人工确认流程。
- 已有明确测试内容，不包含敏感信息和医疗结论。
- 已有回滚开关，默认可回到 `external_disabled`。
- 已有 `MessageDelivery` 状态回写要求。
- 已有 timeline、audit、dashboard 验收口径。
- 已有 consent / opt-out / frequency cap 判断。
- 已明确测试期间不允许自动营销、自动群发、AI 直发客户。

任一条件不满足，不得进入真实渠道发送开发。

## 8. 单租户 / 单机构 / 单客户 / 单条消息控制方案

真实渠道灰度必须采用多层 gated 控制：

- 租户层：只有指定 `tenantId` 在 `allowlist` 中才可能继续。
- 机构层：只有指定 `institutionId` 在 `allowlist` 中才可能继续。
- 客户层：只允许指定测试客户，且必须具备 consent。
- 员工层：只允许指定测试员工触发人工确认。
- 消息层：只允许一条明确测试消息，不允许批量选择。
- 渠道层：只允许一个 `channelType`，不得同时打开企业微信和短信。
- 状态层：未通过任一条件时，`deliveryMode` 必须保持 `external_disabled` 或 mock/manual。

控制逻辑必须遵循 safe failure：任何缺失、异常、配置不匹配、校验失败，都默认不发送。

## 9. 真实发送前人工确认流程

真实发送前必须经过人工确认，流程建议如下：

1. 运营人员查看低敏消息草稿。
2. 系统展示渠道灰度提示、客户授权状态、退订状态和频率限制结果。
3. 运营人员确认测试客户、测试员工、测试渠道、测试内容。
4. 系统再次检查 `tenantId`、`institutionId`、测试客户、测试员工、`channelType`、consent、opt-out、frequency cap。
5. 仅当所有条件通过时，才允许进入真实渠道 sandbox provider contract。
6. 发送后必须写入 `MessageDelivery`、timeline、audit 和 dashboard。

没有人工确认不得发送。人工确认不得被后台任务、自动营销规则或 AI 生成链路绕过。

## 10. 开关与回滚方案

目标 4 必须提供明确开关与回滚策略：

- 全局默认关闭真实外部渠道。
- 租户灰度开关默认关闭。
- 机构灰度开关默认关闭。
- 渠道开关默认关闭。
- 测试客户开关默认关闭。
- 任一开关关闭时，状态必须回到 `external_disabled`。
- 回滚不应删除历史记录，只追加低敏 audit 和 timeline。
- 回滚后页面和 dashboard 必须清楚显示真实渠道已关闭。

回滚目标不是恢复成「看起来发送成功」，而是让系统重新进入可解释的安全阻断状态。

## 11. 发送内容安全边界

真实发送内容必须只使用低敏白名单字段，不得包含：

- 手机号原文。
- 身份证号。
- 病历号。
- HIS payload。
- 完整病历。
- 咨询全文。
- provider / model / token / cost / vendor。
- secret / API key。
- AI 原始 prompt 或 raw response。
- 明确医疗诊断或治疗建议。

内容必须保持人工随访语气，只能表达护理提醒、人工联系说明、到店或人工咨询建议，不得替代医生判断。

## 12. 客户触达合规边界

真实渠道灰度必须遵守以下合规边界：

- 没有 consent 不发送。
- opt-out 不发送。
- frequency cap 命中不发送。
- 未进入灰度不触达。
- 外部渠道未启用则 `external_disabled`。
- 没有人工确认不发送。
- 不做自动营销。
- 不做自动群发。
- 不做客户自动回复。
- 不发送 AI 自动生成且未经人工确认的客户可见医疗建议。

短信额外要求：

- 必须有测试手机号。
- 必须有明确签名和模板。
- 必须有退订策略。
- 必须有成本上限。
- 必须确认供应商回执低敏化。

## 13. MessageDelivery 状态回写要求

目标 4 开发时，`MessageDelivery` 必须成为真实渠道灰度的唯一状态锚点。

建议状态要求：

- 灰度未命中：`external_disabled`。
- 未授权：`skipped`，failure reason 为 consent 相关低敏原因。
- 退订：`skipped`，failure reason 为 opt-out 相关低敏原因。
- 频控命中：`skipped`，failure reason 为 frequency cap 相关低敏原因。
- provider sandbox 请求失败：写入低敏 failure reason，不输出供应商原始错误。
- provider sandbox 请求成功：只记录低敏成功状态，不保存真实 payload。
- 回滚后：新增回滚 audit，不删除原始 `MessageDelivery`。

状态回写必须可被 timeline、audit、dashboard 和页面读取，但不得泄露真实渠道凭证或供应商原始响应。

## 14. timeline / audit / dashboard 验收要求

timeline 验收要求：

- 能看到人工确认节点。
- 能看到触达安全治理结果。
- 能看到真实渠道灰度是否命中。
- 能看到发送成功、失败、跳过、回滚的低敏状态。

audit 验收要求：

- 记录操作者。
- 记录 `tenantId`、`institutionId` 的隔离上下文。
- 记录触达安全 reason。
- 记录灰度开关 reason。
- 不记录 secret、API key、真实 payload、供应商 raw response。

dashboard 验收要求：

- 能展示 allowed、skipped、external_disabled、失败、回滚等低敏计数。
- 能区分 consent missing、opt-out、frequency cap、gray guard、channel disabled。
- 空库或无灰度数据时展示低敏空态，不返回 503。

## 15. 失败与异常处理

失败处理必须默认安全：

- 配置缺失：不发送，写 `external_disabled`。
- secret 缺失：不发送，写低敏配置缺失原因。
- provider 超时：不重试真实发送，写低敏失败。
- provider 返回异常：不输出原始响应，写低敏失败。
- 状态回写失败：不得再次触发真实发送，必须保留审计补偿入口。
- 人工确认过期：不发送。
- 客户状态变化为 opt-out：不发送。
- frequency cap 变化为命中：不发送。

禁止在失败后自动补发真实消息。任何重试都必须另行人工确认。

## 16. 低敏字段白名单

建议真实渠道灰度阶段只允许以下低敏字段进入 DTO、timeline、audit、dashboard：

- `deliveryId`
- `tenantId`
- `institutionId`
- `customerId`
- `followUpTaskId`
- `messageDraftId`
- `channelType`
- `deliveryMode`
- `status`
- `failureReason`
- `safeReasonLabel`
- `auditReason`
- `createdAt`
- `updatedAt`
- `sentAt`
- 低敏 `contentSnapshot`
- 低敏 `recipientRef`

其中 `recipientRef` 不得是手机号原文或外部账号原文，只能是内部低敏引用。

## 17. 禁止能力清单

1. 生产级真实渠道触达全面上线。
2. 企业微信全量接入。
3. 短信全量接入。
4. 客户自动回复。
5. 自动营销群发。
6. AI 自动生成并直接发送客户可见医疗建议。
7. HIS 真实同步。
8. 真实客户回复回流。
9. 支付账单。

## 18. 5010 / 本地 / 沙箱验收建议

目标 4 开发时，验收建议分三层：

第一层：本地 5010 验收。

- `/api/version` 返回 200。
- `/hospital` 返回 200。
- 智能随访页面可打开。
- 触达安全治理、灰度前置、默认关闭、人工确认文案可见。
- dashboard API 返回 200。
- 不使用真实 secret。
- 不真实发送。

第二层：provider sandbox contract 验收。

- 使用 fake provider 或测试账号。
- 只允许 localhost 或明确 sandbox endpoint。
- 不输出 secret。
- 不保存 raw response。
- 不触达真实客户。

第三层：真实小范围灰度 proof。

- 只允许一个渠道。
- 只允许一个测试客户。
- 只允许一条测试消息。
- 发送前人工确认。
- 发送后状态可回写。
- 可立即回滚。

## 19. 后续开发任务拆分

建议后续任务拆分如下：

1. 目标 4A：真实渠道灰度前置确认文档，本任务。
2. 目标 4B：单渠道 provider sandbox contract。
3. 目标 4C：单租户 / 单机构 / 单客户真实发送 gated proof。
4. 目标 4D：发送状态回写、失败处理、回滚收口。
5. 目标 4E：目标 4 closeout 文档。

每个任务必须独立审批，不得因为本文档存在就自动开始开发。

## 20. 是否可以进入目标 4 开发的判断标准

只有同时满足以下条件，才可以进入目标 4 开发：

- 已经明确第一灰度渠道，且只选择一个渠道。
- 已经明确测试租户、测试机构、测试客户、测试员工和测试消息。
- 已经确认 consent、opt-out、frequency cap 的真实执行口径。
- 已经确认默认关闭和回滚开关。
- 已经确认 `MessageDelivery` 状态回写设计。
- 已经确认 timeline、audit、dashboard 验收口径。
- 已经确认不接 HIS、webhook、客户回复回流、支付账单、完整 BI。
- 已经确认目标 4 不做自动营销、自动群发、AI 直发客户。
- 已经获得用户明确授权进入 runtime 开发。

未获得明确 runtime 授权前，只能停留在规划和评审阶段。
