# V0.8-04F-C-PLAN：单机构测试账号人工确认发送 proof 授权清单与执行门槛

## 1. 文档目的

本文只用于定义进入“单机构测试账号人工确认发送 proof”之前必须完成的授权清单、执行门槛和停止条件。

当前任务只做 proof 前置授权清单，不开发功能，不接真实通道，不配置凭证，不读取凭证，不真实出网，不真实发送。

本文不代表真实 proof 已获授权，也不代表可以开始 4F-C 真实代码开发。

## 2. 当前任务边界

本任务明确只做 docs-only 文档，不做以下事项：

- 不接真实企业微信。
- 不接真实微信。
- 不接短信。
- 不接 HIS。
- 不接 webhook。
- 不配置 secret。
- 不读取 secret。
- 不输出 secret、token、API key 或任何真实凭证。
- 不真实出网。
- 不真实发送。
- 不同步真实客户。
- 不同步外部联系人。
- 不同步聊天记录。
- 不接入会话内容存档。
- 不开始 4F-C 真实代码开发。
- 不开始 4F-D。
- 不修改 schema / migration / package / lock。

## 3. 当前安全门禁

进入任何后续 proof 任务前，以下安全门禁必须保持默认关闭状态：

```txt
allowRealSend=false
externalChannelEnabled=false
realSendAllowed=false
noRealSend=true
noRealNetwork=true
noSecretRead=true
noSecretOutput=true
```

以上门禁的含义是：

- `allowRealSend=false`：当前不允许真实发送。
- `externalChannelEnabled=false`：当前不启用外部真实通道。
- `realSendAllowed=false`：当前业务层不允许真实触达。
- `noRealSend=true`：当前任务禁止真实发送。
- `noRealNetwork=true`：当前任务禁止真实出网。
- `noSecretRead=true`：当前任务禁止读取 secret。
- `noSecretOutput=true`：当前任务禁止输出 secret。

任何将以上门禁调整为真实发送可用状态的动作，都必须另开任务、单独授权、单独验收，不能由本文自动授权。

## 4. 与 4F-A / 4F-B 的关系

4F-A / 4F-B 已完成的是 dry-run 与 no-send 能力，作用是证明系统可以在不真实出网、不真实发送、不读取真实 secret 的条件下表达流程、门禁和阻断原因。

这些能力不代表真实 proof 已授权：

- dry-run 通过不等于允许真实发送。
- no-send 能力存在不等于允许打开真实通道。
- `mock_dry_run_completed` 不等于允许真实发送。
- `mock_dry_run_completed` 只表示模拟干跑完成，不表示测试机构、测试账号、测试接收人、secret 管理、真实出网、真实发送内容和 emergency stop 已经完成授权。

真实发送 proof 必须由用户逐项授权后才可进入。

## 5. 4F-C 的进入门槛

4F-C 只有在以下条件全部满足后，才允许另开真实 proof 授权任务：

1. 用户逐项完成本文第 6 节的 15 项人工确认清单。
2. 用户明确授权是否允许真实出网。
3. 用户明确授权是否允许配置 secret。
4. 用户明确授权是否允许发送一条测试消息。
5. 用户明确测试机构、测试企业微信主体、测试账号和测试接收人。
6. 用户明确发送内容和发送前二次确认机制。
7. 用户明确日志字段、脱敏字段和禁止保存字段。
8. 用户明确 emergency stop 责任人。
9. 用户明确失败回滚方式。
10. 用户明确 proof 成功后是否进入 4F-D。

未全部确认前，必须继续停留在 dry-run / no-send / mock proof 阶段。

## 6. 进入真实发送 proof 前的 15 项人工确认清单

进入任何真实发送 proof 前，用户必须逐项确认以下 15 项：

| 序号 | 确认项 | 必须明确的内容 | 未确认时的处理 |
| --- | --- | --- | --- |
| 1 | 测试机构是哪一家 | 明确唯一测试机构，不写入敏感真实标识 | 停止 proof |
| 2 | 测试企业微信主体是哪一个 | 明确企业微信主体，仅通过安全渠道确认 | 停止 proof |
| 3 | 测试账号是谁 | 明确测试员工或测试账号，不写入真实账号凭证 | 停止 proof |
| 4 | 测试接收人是谁 | 明确唯一测试接收人，避免误触达真实客户 | 停止 proof |
| 5 | 是否允许真实出网 | 明确允许或不允许真实调用企业微信接口 | 未允许则保持 `noRealNetwork=true` |
| 6 | 是否允许配置 secret | 明确是否允许在受控测试环境配置 secret | 未允许则保持不配置 |
| 7 | secret 由谁保管 | 明确保管人、配置渠道、轮换和撤销责任 | 未明确则禁止配置 |
| 8 | 是否允许发送一条测试消息 | 明确是否只允许单条测试消息 | 未允许则保持 `noRealSend=true` |
| 9 | 发送内容是什么 | 明确固定测试消息文本，不包含隐私和营销承诺 | 未明确则不得发送 |
| 10 | 发送前是否需要二次确认 | 明确发送前是否需要用户再次确认 | 未明确则默认需要二次确认 |
| 11 | 日志记录哪些字段 | 明确允许记录的低敏字段白名单 | 未明确则只允许记录 mock 状态 |
| 12 | 哪些字段必须脱敏 | 明确手机号、姓名、外部联系人标识、消息内容等脱敏规则 | 未明确则不得记录真实字段 |
| 13 | 谁负责 emergency stop | 明确异常时的停止责任人和触发方式 | 未明确则不得进入 proof |
| 14 | 失败如何回滚 | 明确关闭开关、撤销配置、删除临时材料和回退路径 | 未明确则不得进入 proof |
| 15 | proof 成功后是否进入 4F-D | 明确是否另行评估进入 4F-D | 未明确则不得自动推进 |

以上 15 项必须全部由用户逐项确认。任何一项缺失，都不能进入真实发送 proof。

## 7. 真实 proof 前禁止事项

在 15 项人工确认清单完成之前，禁止：

- 配置真实 `corpId`、secret、token、`encodingAESKey`、callback token、webhook secret 或 API key。
- 读取 `.env.local` 或任何 secret 存储位置。
- 输出真实 secret、token、API key 或回调敏感参数。
- 调用真实企业微信接口。
- 真实出网到企业微信、微信、短信、HIS、webhook 或第三方服务。
- 向任何客户、员工、外部联系人或测试账号发送真实消息。
- 同步真实客户、外部联系人或聊天记录。
- 接入会话内容存档。
- 将聊天原文送入 AI。
- 将 4F-C 与 4F-D 合并推进。

## 8. 日志与脱敏原则

真实发送 proof 如后续获得单独授权，日志也必须遵守最小化原则。

允许优先考虑的低敏字段包括：

- proof 任务编号或低敏内部标识。
- 测试机构的内部占位标识。
- 通道类型占位值。
- 发送动作的状态枚举。
- dry-run / no-send / real-send 的门禁状态。
- 成功或失败的低敏原因码。
- emergency stop 是否触发。
- 回滚是否完成。

必须脱敏或禁止保存的字段包括：

- 真实客户姓名。
- 手机号。
- 身份证号。
- 病历号。
- 微信标识。
- 企业微信外部联系人标识。
- 聊天原文。
- 测试消息中可能包含的隐私内容。
- secret、token、API key、callback token、webhook secret。
- 企业微信原始接口返回中的敏感字段。

如果无法确认字段是否低敏，默认不得记录。

## 9. emergency stop 与失败回滚

后续真实 proof 如获得单独授权，必须在发送前明确 emergency stop 和失败回滚方案。

emergency stop 至少需要明确：

- 责任人是谁。
- 触发条件是什么。
- 触发后关闭哪些开关。
- 是否撤销测试环境配置。
- 是否停止所有外部调用。
- 是否删除临时材料。
- 如何确认没有继续发送。

失败回滚至少需要明确：

- 保持或恢复 `allowRealSend=false`。
- 保持或恢复 `externalChannelEnabled=false`。
- 保持或恢复 `realSendAllowed=false`。
- 保持或恢复 `noRealSend=true`。
- 保持或恢复 `noRealNetwork=true`。
- 停止真实企业微信调用。
- 撤销或停用测试 secret / token 配置。
- 删除临时测试材料。
- 只保留允许的低敏 audit 结果。
- 回退到 dry-run / no-send / mock proof 状态。

## 10. 4F-D 不自动推进

proof 成功后是否进入 4F-D 需要单独判断，不得自动推进。

4F-D 至少需要另行确认：

- proof 是否只在授权范围内完成。
- 是否发生真实出网、真实发送或日志异常。
- 是否存在误触达风险。
- 是否存在 secret 暴露风险。
- 是否需要扩展到更多机构、更多账号或更多接收人。
- 是否需要进入商用试点判断。
- 是否需要补充合规、审计、隐私和客户授权材料。

即使 4F-C proof 成功，也只能形成“可进入 4F-D 评估”的候选结论，不能自动开始 4F-D。
