# V0.6-PACKAGE-AI-QUOTA-REAL-LINK-PRE-DESIGN-01：真实 quota linkage 前置设计收口

## 1. 背景与当前状态

平台端已经完成 `V0.6-PACKAGE-AI-QUOTA-PLATFORM-READONLY-03`，当前具备 mock/fixture-based 的套餐权益 / AI 服务额度只读 API，用于平台侧理解套餐、权益、租户绑定、额度状态和服务项目额度归因的 contract 形态。

机构端已经完成 `V0.6-PACKAGE-AI-QUOTA-INSTITUTION-LINKED-04`，当前 `GET /api/institution/ai-service-usage` 返回 `quota.isLinked=true`，并在 `/hospital` 的 `AI 服务使用` 视图中展示 linked readonly 额度视图。页面可展示已用、剩余、使用率、周期、状态和 `warningLevel`，并明确当前为只读额度视图。

当前能力仍然是 mock/fixture-based readonly，不是真实套餐扣减，不是真实剩余额度，不是真实财务账单，也不代表 provider 成本已经验收。当前 linked readonly 只能作为产品口径和展示链路的阶段性验收结果，不能外推为生产可直接上线能力。

## 2. 本设计目标

本设计用于在进入真实套餐权益数据接入之前，先锁定真实 quota linkage 的前置边界：

1. 明确机构端可以看到哪些低敏额度字段。
2. 明确平台端内部字段不得透传给机构端。
3. 明确真实 DB quota 接入前必须先补齐的数据来源、绑定关系、周期、重置、审计和回退策略。
4. 明确 mock/fixture fallback 在真实接入阶段仍需要保留为安全兜底，而不是被静默删除。
5. 明确后续任务必须拆小，不允许一次性混入 schema、API、UI、扣减、告警、导出和生产上线。

本设计只做前置设计收口，不实现任何 runtime 能力。

## 3. 机构端可见字段白名单

机构端 AI 服务额度视图只能展示低敏额度字段。建议白名单如下：

1. `isLinked`：表示当前是否接入额度视图。`true` 仅表示已接入额度展示链路，不表示真实扣减已经完成。
2. `status`：额度状态，例如 `active`、`warning`、`overLimit`、`expired`。该字段只用于状态展示，不直接触发阻断。
3. `periodStart`：额度周期开始时间。
4. `periodEnd`：额度周期结束时间。
5. `totalAllowance`：当前周期总额度，单位由 `displayUnit` 决定。
6. `used`：当前周期已用额度。
7. `remaining`：当前周期展示剩余额度。真实接入前后都必须明确它是额度视图字段，不等同于财务余额。
8. `usageRate`：使用率，建议由 server 侧统一计算并限制精度。
9. `warningLevel`：提示等级，例如 `low`、`medium`、`high`、`exceeded`。该字段只表示展示提示等级，不等同于真实告警已完成。
10. `displayUnit`：机构端展示单位，建议使用 `AI 服务额度` 等产品化表达，不展示 Token 或供应商成本单位。
11. `notes`：低敏说明文案，用于提示只读、非扣减、非账单、非真实财务结算。

这些字段只表达“AI 服务额度视图”，不表达 provider 成本、Token 成本、内部折算规则、供应商账单或财务账单。

## 4. 平台端内部字段边界

平台端可以管理套餐、权益、AI 服务额度、计量规则、内部成本和供应商相关信息，但这些字段不得透传给机构端。

平台内部字段至少包括：

1. `provider`。
2. `model`。
3. `modelCode`。
4. Token 原始用量与 `totalTokens`。
5. AI Credits 内部折算规则。
6. 模型单价、供应商单价、成本配置。
7. RMB、人民币金额、`¥`、真实成本金额。
8. 供应商账单、供应商发票、供应商结算字段。
9. 内部计量策略、扣减策略、阈值策略。
10. 平台运维和调试字段。

真实接入后，平台端可以继续保留这些字段用于内部运营、审计和治理，但机构端 facade / DTO / UI 必须只输出机构端白名单字段。

## 6. 真实数据接入前置条件

后续若要接真实 DB quota，至少必须先明确以下前置条件：

1. 数据来源：真实额度来自套餐配置、租户套餐绑定、人工配置、运营导入还是其他系统。
2. 租户与套餐绑定关系：一个租户在一个周期内是否只能有一个有效套餐，套餐变更如何影响当前周期额度。
3. 套餐周期：月度、自然月、订阅周期、试用周期等口径必须统一。
4. 额度单位：机构端展示单位建议为 `AI 服务额度`，不得用 Token 或供应商成本作为机构端单位。
5. 额度重置规则：周期开始、周期结束、试用到期、套餐升级/降级时如何重置或结转。
6. 额度变更规则：套餐变更、人工加量、赠送额度、冻结、作废等如何计算展示额度。
7. 人工修正机制：需要平台管理员可审计地修正额度或状态，不能直接静默改值。
8. 审计记录边界：真实接入后，额度变更、人工修正、套餐绑定变更必须有低敏审计记录。
9. mock/fixture fallback：真实数据异常、未配置、测试环境缺失时，应明确回退为 `isLinked=false` 或受控 mock fallback，不得伪装成真实额度。
10. 测试环境与生产环境隔离：测试库、测试服、生产库的套餐和额度数据必须隔离，不能用测试数据推导生产可用性。

如果这些条件未完成，不能开始真实扣减、告警、导出或生产上线。

## 7. 后续真实接入建议拆分

后续不建议一次性做大任务。建议拆成以下阶段：

1. DB/schema 设计文档：只设计真实套餐权益、额度周期、额度变更、审计字段，不写 migration。
2. server-domain 真实数据读取 contract：定义真实数据读取 DTO、低敏 mapper、fallback 行为和测试 fixture。
3. 平台端真实绑定只读 API：只读展示套餐绑定和额度配置，不做写入和扣减。
4. 机构端真实 quota readonly 接入：将 `GET /api/institution/ai-service-usage` 的 quota 来源从 mock/fixture 演进为真实只读 facade。
5. 审计与人工修正设计：设计人工修正、变更原因、操作人、前后值摘要和审计查询口径。
6. 额度扣减设计：单独设计扣减时机、幂等性、失败回滚、并发和边界，不与 readonly 接入混做。
7. 告警设计：单独设计阈值、通知对象、频率、静默期和误报处理。
8. 导出设计：单独设计导出字段白名单、权限、审计和脱敏规则。
9. 生产上线验收：单独做安全、权限、数据、运维、备份和回滚验收。

本轮只写前置设计，不实现上述任何阶段。

## 8. 风险与防误导说明

必须在产品、运营和验收口径中持续强调：

1. 当前 linked readonly 不等于真实扣减。
2. `remaining` 不等于真实可用余额。
3. `overLimit` 不等于真实阻断。
4. `warningLevel` 不等于真实告警。
5. 当前页面不构成财务账单。
6. 当前 API 不构成人民币成本核算。
7. 当前不代表 provider 成本已经验收。
8. 当前不可对外宣称生产可直接上线。
9. 当前不可向机构端展示 Token、provider、model、成本和内部折算规则。
10. 当前不能把 mock/fixture readonly 能力外推成真实上线能力。
