# V0.8 目标 4D：客户触达通道路线统一核验与单机构验证方案

## 1. 文档目的

本文用于统一核验 V0.8 客户触达通道路线，并把原 4D、4E、4F 中的方案设计部分合并收口。

本文只做路线核验、风险评估和单机构真实通道验证方案设计，不开发功能，不修改代码，不新增 API，不新增 UI，不新增 schema / migration，不接真实企业微信，不接真实微信，不接短信、HIS 或 webhook，不配置 secret、token 或 API key，不写真实 callback，不真实发送，不真实出网，不同步真实客户、外部联系人或聊天记录，不接入会话内容存档，也不开始真实 proof 实现。

本文重点回答：

- 官方企业微信路线能做什么、不能做什么。
- 自建应用、第三方应用、服务商路线有什么差异。
- 客户联系、外部联系人、企业微信客服、会话内容存档分别适合承载什么。
- 青焱式扫码、端口、机器编号、uip 和账号托管路线有哪些风险。
- 4B AI 会话工作台和 4C 自动回复 / 自动随访策略如何映射到真实通道。
- 单机构真实通道验证 proof 的最小范围是什么。
- 真实接入前必须让用户人工确认哪些事项。

## 2. 当前基线

当前基线为 `main / origin/main = 76003eec1ec27e2b9d459a57032228571cea028c`。

当前系统已经具备低敏客户、智能随访、消息草稿、MessageDelivery、timeline、audit、dashboard、企业微信授权状态 mock、企业微信客户联系 mock、企业微信随访触达 mock、AI 会话工作台模拟版、自动回复与自动随访策略模拟版。

当前系统仍然没有真实企业微信、真实微信、真实短信、HIS、webhook、扫码托管、端口、机器编号、uip、第三方托管服务商、真实自动回复、真实自动随访、真实群发、真实自动加好友、会话内容存档或聊天原文训练链路。

## 3. 已完成能力回顾：4A / 4B / 4C

4A 已完成需求方向对齐：用户需要的是机构端 AI 会话工作台和客户运营能力，不是企业微信登录，也不是单纯发消息按钮。4A 已明确青焱参考能力可以用于产品拆解，但扫码托管、端口、机器编号、uip、群发、主加触达和聊天记录同步必须进入后置风险评估。

4B 已完成 AI 会话工作台模拟版：包含账号列、会话列表、聊天窗口、AI / 档案面板、推荐回复、人工接管、风险预警、推荐项目、用户画像、低敏时间线和低敏统计。页面明确当前仅模拟，不接真实企业微信 / 微信，不接短信、HIS、webhook，不真实发送，不真实出网。

4C 已完成自动回复与自动随访策略模拟版：定义 L0 AI 推荐、L1 AI 草稿 + 人工确认、L2 低风险自动回复、L3 受控自动随访、L4 营销自动化 / 群发 / 加好友 / 裂变。策略已覆盖退订、频控、授权、安全开关、`allowRealSend=false`、`externalChannelEnabled=false`、低敏输出、审计和阻断原因。

## 4. 为什么合并原 4D / 4E / 4F 方案设计

原 4D、4E、4F 分别倾向于官方企业微信能力核验、账号托管路线评估和真实通道 proof 设计。三者如果拆开写，容易出现三类偏差：

- 只看官方接口，忽略青焱式账号托管能力带来的产品期望和风险。
- 只看账号托管，误以为扫码、端口、机器编号或 uip 是 AI 会话工作台的必要前置。
- 只设计 proof，缺少官方路线、托管路线、自动回复分级和单机构安全边界的统一判断。

因此本任务先合并方案设计，形成一份统一口径。后续是否做真实 proof，必须基于本文的人工确认清单再单独授权。

## 5. 官方企业微信路线核验

官方企业微信路线更适合长期 SaaS 合规交付。原因是它围绕企业主体、应用授权、接口权限、可见范围、回调配置和审计边界展开，更适合多机构 SaaS 逐步接入。

官方路线可核验的能力包括：

- 客户联系与外部联系人：用于获取外部联系人低敏资料、跟进员工、客户备注、标签、添加时间和关系。
- 企业微信客服：用于微信内外咨询入口、客服账号、会话分配、接收消息和发送客服消息。
- 第三方应用 / 服务商：用于多机构授权、应用安装、授权企业凭证、权限范围、数据回调和指令回调。
- 会话内容存档：用于企业在合规授权下获取会话内容，但它不是普通聊天记录同步，必须单独设计。

官方路线不能直接承诺：

- 不能绕过客户授权、员工知情、企业授权和权限范围。
- 不能把客户联系当作聊天原文同步。
- 不能把企业微信客服当作全量客户运营自动化。
- 不能把会话内容存档当作普通消息列表。
- 不能让 AI 未经人工确认直接发送客户可见医疗建议。
- 不能把 L4 营销自动化、群发、加好友、裂变混入医疗随访主链路。

参考依据：

- 企业微信官方“获取客户详情”文档说明，客户详情接口要求应用满足客户联系相关权限，自建应用需配置到客户联系可调用接口的应用中，第三方应用需具备客户基础信息权限，且部分字段对第三方应用不可获取。
- 企业微信官方“微信客服”文档说明，企业可通过 API 管理微信客服账号、分配客服会话、收发客服消息，但需要在管理后台开启 API 并配置可调用应用。
- 企业微信官方“获取会话内容”文档显示，会话内容存档有独立 secret、存档 access_token、同意情况、客户同意回调和会话内容结构。
- 企业微信官方第三方应用接入说明要求服务商、授权、权限最小化、可信域名、回调 URL、测试企业、上线审核等流程。

## 6. 企业微信自建应用路线

自建应用路线适合单机构或少量机构的内部开发 proof。

优势：

- 开发路径较短，适合验证单机构、单应用、单测试账号。
- 机构管理员可在自身企业微信后台配置应用、可见范围、客户联系可调用接口应用和微信客服 API。
- 对第一阶段 proof 更可控，便于验证授权状态、可见范围、客户映射和人工确认链路。

限制：

- 不适合长期多机构 SaaS 规模化交付，因为每家机构都需要单独配置。
- 真实 secret、回调、可信 IP、可见范围和权限变更都需要机构管理员配合。
- 客户联系、微信客服、会话内容存档的权限范围不同，不能用一个“自建应用已配置”概括全部能力。
- 后续迁移到服务商 / 第三方应用时，授权模型、凭证模型、回调模型和数据隔离都需要重新设计。

适用判断：自建应用可以作为第一阶段单机构 proof 的候选路线，但只用于验证最小链路，不作为长期 SaaS 默认路线。

## 7. 企业微信第三方应用路线

第三方应用路线适合平台方提供统一应用，由机构管理员授权安装后，平台按授权范围获得客户运营能力。

优势：

- 更适合多机构 SaaS。
- 授权、安装、权限范围、回调、应用可见范围和授权变更可以形成统一模型。
- 可以把 `tenantId`、`institutionId`、授权企业标识、授权状态、能力范围、过期 / 撤销 / 禁用、最近同步时间、最近错误原因等沉淀成平台侧低敏状态。

限制：

- 需要服务商体系、第三方应用配置、授权流程、测试企业、权限申请、上线审核。
- 需要区分服务商 token、第三方应用 token、授权企业 token。
- 需要严格权限最小化，不能一次性申请与第一阶段 proof 无关的能力。
- 数据回调、指令回调、授权变更、ticket 推送、可信域名和隐私政策都需要正式设计。

适用判断：第三方应用路线是长期目标，但不建议第一阶段直接完成完整服务商接入。第一阶段可以先用文档和 mock 固化模型，再用单机构 proof 验证必要最小能力。

## 8. 企业微信服务商路线

服务商路线是第三方应用规模化交付的组织形态。平台方需要成为企业微信服务商，在服务商后台创建应用，完成应用配置、测试授权、上线审核和后续运营。

优势：

- 面向多机构交付，便于统一授权、统一升级、统一回调、统一审计。
- 支持第三方标准应用和自建应用代开发等交付形态。
- 更容易形成 SaaS 产品化能力，而不是每家机构手工填配置。

限制：

- 申请、认证、审核、应用上线、权限申请和回调域名配置都需要运营和合规准备。
- 需要服务商隐私政策、数据安全说明、权限最小化证明和测试企业。
- 需要真实 secret 管理方案、回调验签 / 解密方案、租户隔离方案、日志脱敏方案和撤销授权处理。

适用判断：服务商路线应作为长期合规交付方向，但当前不立刻申请或接入。进入服务商路线前，应先完成单机构 proof 的业务确认和安全边界验证。

## 9. 客户联系 / 外部联系人能力边界

客户联系和外部联系人适合承载“客户资产低敏映射”，不等于普通微信好友同步，也不等于聊天记录同步。

第一阶段可规划：

- 外部联系人低敏标识映射到系统 `customerId`。
- 客户归属员工映射到系统员工。
- 客户标签、客户备注、客户来源、添加时间、关系状态的低敏摘要。
- 客户联系授权状态、最近同步时间、最近错误原因。

第一阶段不能做：

- 展示真实手机号原文、身份证、病历号、完整地址。
- 保存企业微信原始接口返回全文。
- 展示或训练聊天原文。
- 同步个人微信好友。
- 自动加好友或主加触达。
- 群发营销或裂变拉新。

## 10. 企业微信客服能力边界

企业微信客服适合承载“咨询入口、会话分配、客服接待、消息收发”的官方路线。它可映射 4B 的 AI 会话工作台，但不能直接等同于完整私域运营自动化。

可借鉴方向：

- 将外部咨询接入客服工作台。
- 将客服会话分配给接待人员。
- 将消息事件进入低敏会话队列。
- 结合客户详情页、AI 推荐回复、人工接管和风险预警辅助客服。

必须限制：

- 真实收发消息前必须确认 API 已开启、客服账号已配置、接待人员在应用可见范围内。
- 不允许未授权的 AI 自动回复客户。
- 不允许绕过 4C 的 L0-L4 分级、退订、频控、安全开关和人工确认。
- 医疗建议、投诉、价格承诺、术后异常必须转人工。

## 11. 会话内容存档能力边界

会话内容存档不是普通聊天记录同步，也不是当前 proof 的默认范围。

会话内容存档涉及：

- 企业授权。
- 员工知情。
- 客户合规边界。
- 会话同意情况。
- 客户同意进行聊天内容存档事件回调。
- 内容解密、存储、脱敏、检索、删除和导出。
- 权限控制、审计、数据保留期限和医疗建议风险。

因此，会话内容存档必须后置。后续如要接入，应单独立项，且必须明确：

- 哪些员工、哪些客户、哪些会话进入范围。
- 是否只存摘要，不存原文。
- 原文是否允许进入 AI，是否需要人工脱敏。
- 数据保留期限、删除策略和导出策略。
- AI 只辅助员工，不直接自动回复客户。

## 12. 账号托管路线核验：扫码 / 端口 / 机器编号 / uip

青焱式账号托管路线包括个微 / 企微切换、企微上号、扫码登录、账号密码登录、端口购买 / 续费、机器编号、uip、平台号、助手号、扫码号、账号在线状态、掉线重登、封号预警、好友群发、关键词回复、主加触达、敏感词拦截、AI 知识库和 AI 推荐回复。

这些能力可以作为竞品参考，但不建议第一阶段自研底层托管能力。

高风险点：

- 扫码：涉及登录态、掉线、二次验证、账号权重、员工个人账号边界和异常登录风险。
- 端口：涉及外部资源购买 / 续费、账号上线能力、业务连续性和供应商绑定。
- 机器编号：可能涉及设备指纹、运行环境绑定、风控识别和运维依赖。
- uip：属于外部程序或托管运行环境相关能力，存在安全、合规、可维护性和责任归属风险。
- 账号风控：PDF 中多处出现掉线、封号、限流、敏感词、群发延时、好友添加阈值和企业主体风险。
- 自动群发：容易触发投诉、删除率、内容风控和平台限制。
- 自动加好友：属于主加触达，与医疗随访主链路风险等级不同。

结论：扫码、端口、机器编号、uip 是高风险路线，必须单独评估。它们不能作为 V0.8 真实通道 proof 的默认实现路径。

## 13. 官方路线与账号托管路线对比表

| 维度 | 官方企业微信路线 | 账号托管路线 |
| --- | --- | --- |
| 长期 SaaS 适配 | 更适合，围绕机构授权和应用权限 | 较弱，依赖账号、端口、机器或外部托管 |
| 合规边界 | 相对清晰，可按客户联系、微信客服、会话存档拆分 | 边界复杂，可能混入个人号、扫码号、平台号 |
| 稳定性 | 依赖官方 API、权限和回调 | 易受掉线、封号、限流、端口到期影响 |
| 成本 | 前期服务商 / 应用 / 合规成本较高 | 前期可看似快速，但账号维护和风险成本高 |
| 交付难度 | 架构复杂但可产品化 | 单点交付快，规模化和责任边界难 |
| 数据安全 | 可设计权限、审计、脱敏和撤销 | 登录态、聊天内容、联系人和供应商边界难控 |
| 自动回复 | 可在授权和安全策略后逐步灰度 | 容易绕过平台治理，风险高 |
| 群发 / 加好友 | 应独立高风险评估 | 常见但风险最高，不适合医疗随访主链路 |
| 推荐优先级 | 第一优先 | 后置评估 |

## 14. 青焱参考能力哪些可借鉴

可借鉴的产品能力：

- 客服工作台布局：账号列、会话列表、聊天窗口、档案 / AI 面板。
- 会话状态：全部、AI、待接管、人工。
- 推荐回复：AI 生成候选话术，一键填入草稿。
- 人工接管：发送前由客服明确接管。
- 风险预警：过敏、投诉、价格、术后异常、疗效承诺等风险提示。
- 推荐项目：只做低敏建议，避免承诺疗效或价格。
- 用户画像：消费能力、项目偏好、复购意向等低敏摘要。
- 敏感词拦截：作为发送前风险治理。
- 快捷回复和话术库：作为 L0 / L1 辅助能力。
- 工作量统计：接待量、响应时间、接管次数、风险拦截次数。
- AI 知识库和调用统计：作为推荐来源和审计依据。

## 15. 青焱参考能力哪些必须高风险评估

必须高风险评估的能力：

- 企微 / 个微托管切换。
- 企微上号。
- 扫码登录和账号密码登录。
- 端口购买、续费和到期下线。
- 机器编号。
- uip 程序。
- 平台号、助手号、扫码号。
- 自动群发。
- 主加触达。
- 自动加好友。
- 裂变群、活码进群和渠道码。
- 聊天记录全量查看。
- AI 自动发送多媒体素材。
- 销冠话术学习和聊天内容进入 AI。

这些能力不是永远不能规划，而是不能作为第一阶段真实通道 proof，也不能与医疗随访主链路混在一起。

## 16. AI 会话工作台如何映射真实通道

4B AI 会话工作台可映射到真实通道的方式：

- 会话列表：来自企业微信客服会话、客户联系关系或内部模拟会话，第一阶段只允许单机构测试会话。
- 聊天窗口：第一阶段只显示低敏消息摘要和系统事件，不展示聊天原文。
- 推荐回复：保持 L0 / L1，默认只写草稿，不直接发客户。
- 人工接管：真实发送前必须有员工人工确认。
- 客户档案：来自系统客户中心和低敏客户映射，不直接展示企业微信原始返回。
- 风险预警：发送前阻断医疗风险、投诉、价格承诺、术后异常和隐私字段。
- 推荐项目：只能作为内部参考，不得作为客户可见医疗建议自动发送。
- timeline / audit / dashboard：记录低敏状态、人工确认、阻断原因和 MessageDelivery 状态。

真实通道映射原则：

- 先验证状态和映射，再验证发送前置条件。
- 先人工确认，再考虑任何低风险自动策略。
- 先单条消息，再考虑扩大范围。
- 未进入灰度时仍保持 `external_disabled` 或等价禁用状态。

## 17. 自动回复与自动随访策略如何映射真实通道

4C 策略映射到真实通道时必须保留：

- L0：只推荐，不发送。
- L1：生成草稿，人工确认后才可进入 MessageDelivery。
- L2：低风险自动回复只可在 proof 后独立灰度，第一阶段仍不建议真实自动发。
- L3：受控自动随访必须满足授权、未退订、频控通过、低风险、灰度开关和审计。
- L4：营销自动化、群发、加好友、裂变继续阻断，不进入医疗随访主链路。

真实自动回复不能绕过：

- 退订。
- 频控。
- 客户 consent。
- emergency stop。
- `allowRealSend=false` 默认策略。
- `externalChannelEnabled=false` 默认策略。
- 人工确认。
- 低敏输出。
- audit。
- MessageDelivery 状态回写。

## 18. 单机构真实通道验证 proof 最小范围

最小 proof 只设计，不实现。

建议范围：

1. 单机构。
2. 单测试企业微信环境或单测试账号。
3. 只验证授权状态。
4. 只验证低敏客户映射。
5. 只验证人工确认后的模拟转真实发送前置条件。
6. 默认不打开真实发送。
7. 必须保留 emergency stop。
8. 必须保留 `allowRealSend=false` 的默认策略。
9. 必须有人工开关和回滚方案。
10. 不同步真实聊天原文。
11. 不接会话内容存档。
12. 不做群发。
13. 不做自动加好友。
14. 不做营销裂变。

最小 proof 的验收对象不是“客户已收到真实消息”，而是：

- 授权状态是否能低敏读取。
- 测试客户是否能低敏映射。
- AI 会话工作台是否能展示通道可用 / 不可用状态。
- 4C 策略是否能继续阻断真实自动发送。
- 人工确认、MessageDelivery、timeline、audit、dashboard 是否能串起来。
- 一键回滚后是否立即回到不触达状态。

## 19. 第一阶段建议做什么

第一阶段建议只做：

- 官方企业微信路线的单机构 proof 设计确认。
- 自建应用或测试第三方应用的最小授权状态验证。
- 低敏客户映射模型确认。
- 通道状态和客户关系状态展示。
- 人工确认后的发送前置条件检查。
- MessageDelivery 状态回写设计。
- timeline / audit / dashboard 低敏验收口径。
- emergency stop、`allowRealSend=false`、`externalChannelEnabled=false` 默认关闭策略。
- 回滚方案和人工开关设计。

## 20. 第一阶段不建议做什么

第一阶段不建议做：

- 真实自动回复。
- 真实自动随访。
- 真实群发。
- 真实自动加好友。
- 营销裂变。
- 扫码托管。
- 端口 / 机器编号。
- uip 程序。
- 第三方托管服务商接入。
- 会话内容存档。
- 同步真实聊天原文。
- 聊天原文直接进入 AI 训练。
- 多机构同时接入。
- 生产压测。

## 21. 进入真实接入前的人工确认清单

进入任何真实接入前，用户必须人工确认：

1. 选择官方企业微信路线还是账号托管路线。
2. 如选择官方路线，是否先用自建应用做单机构 proof。
3. 是否已有测试企业微信主体。
4. 是否已有测试员工。
5. 是否已有测试客户，且不会误发真实客户。
6. 是否只允许单机构、单通道、单员工、单客户、单条消息。
7. 是否默认保持 `allowRealSend=false`。
8. 是否默认保持外部通道关闭。
9. 哪个角色有权打开灰度开关。
10. 哪个角色有权执行 emergency stop。
11. 是否允许读取客户联系 / 外部联系人低敏资料。
12. 是否允许建立系统客户与外部联系人的映射。
13. 是否明确不读取聊天原文。
14. 是否明确不接会话内容存档。
15. 是否明确不做自动群发。
16. 是否明确不做自动加好友。
17. 是否明确不做营销裂变。
18. 是否明确不接扫码托管、端口、机器编号、uip。
19. 是否明确真实 secret、token、callback、webhook 必须单独设计。
20. 是否明确所有客户可见内容必须人工确认或进入后续独立灰度。
21. 是否明确出现异常时立即回滚到不触达状态。

## 22. 后续任务拆分建议

后续建议拆分：

- 目标 4E：单机构官方企业微信 proof 前置确认文档。只确认测试主体、测试员工、测试客户、授权范围、开关、回滚和验收，不开发。
- 目标 4F：官方企业微信授权状态本地契约增强。只做 mock / contract，不接真实接口。
- 目标 4G：低敏客户映射 proof 设计。只设计映射和验收，不同步真实客户。
- 目标 4H：真实发送前置条件验证设计。只验证人工确认、MessageDelivery、timeline、audit、dashboard 和回滚，不真实发送。
- 目标 4I：账号托管路线独立风险评估。单独评估扫码、端口、机器编号、uip、第三方托管、账号风控和退出方案。
- 目标 4J：会话内容存档独立准入文档。单独评估企业授权、员工知情、客户合规、脱敏、权限、审计、保留、删除和导出。

任何后续任务都不能默认继承真实接入授权。每个真实通道动作都必须单独确认。

## 23. 阶段结论

V0.8 目标 4D 的结论是：

- 官方企业微信路线更适合长期 SaaS 合规交付。
- 自建应用适合单机构 proof，第三方应用 / 服务商路线适合长期多机构授权交付。
- 客户联系 / 外部联系人适合低敏客户映射，不等于个人微信好友同步，也不等于聊天记录同步。
- 企业微信客服适合承载咨询入口、会话分配和客服消息，但不能绕过人工确认和安全策略。
- 会话内容存档不是普通聊天记录同步，必须后置并单独立项。
- 青焱式账号托管能力可以作为竞品参考，但扫码、端口、机器编号、uip、账号风控、群发、主加触达和自动加好友都是高风险能力，不建议第一阶段自研底层托管能力。
- 4B AI 会话工作台和 4C 自动回复 / 自动随访策略可以映射到真实通道，但必须先做单机构、单通道、低风险、人工确认、可回滚的最小 proof。
- 第一阶段真实 proof 不应以“真实发送成功”为目标，而应以“授权状态、低敏客户映射、发送前置条件、人工确认、MessageDelivery、timeline、audit、dashboard 和回滚链路可验证”为目标。
- 在用户人工确认清单完成前，不应开始真实企业微信、真实微信、真实短信、HIS、webhook、扫码托管、端口、机器编号、uip、真实自动回复、真实随访、真实群发、真实自动加好友或会话内容存档实现。
