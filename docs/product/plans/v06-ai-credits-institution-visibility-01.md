## 3. 设计目标

机构端 AI 用量能力的目标不是让机构理解平台内部计量系统，而是帮助机构用产品化语言理解 AI 服务价值和额度消耗：

1. 帮助机构理解 AI 服务使用情况。
2. 帮助机构理解套餐或额度消耗。
3. 帮助机构判断哪些 AI 功能被使用。
4. 帮助机构理解智能随访、知识库问答、客户运营辅助等 AI 辅助动作的使用情况。
5. 保持低敏、可解释、非技术化。
6. 不暴露平台内部模型、Token、供应商、成本和 AI Credits 折算规则。
7. 不把机构端页面设计成财务账单、成本核算或发票依据。
8. 不因为平台端已经有完整运营视图，就默认机构端也能看到同等明细。

## 4. 机构端建议展示范围

机构端建议展示产品化、低敏、可解释的指标。

### 4.1 总览指标

建议展示：

1. 本月 AI 服务使用次数。
2. 近 7 天 / 本月趋势。
3. 已用 AI 服务额度。
4. 剩余 AI 服务额度，前提是套餐权益或额度系统已支撑。
5. 成功率。
6. 成功 / 失败 / 拒绝次数。
7. 接近额度提示，作为后续能力。

### 4.2 服务项目排行

建议展示机构能理解的服务项目排行：

1. AI 问答。
2. 知识库问答。
3. 治疗后随访建议。
4. 智能随访任务生成。
5. 客户运营辅助。
6. 未归因服务。

展示字段建议：

1. 服务项目名称。
2. 服务分类。
3. 使用次数。
4. 成功率。
5. 消耗额度。
6. 占比。

不建议展示 serviceSource、serviceAction、serviceVersion 等内部字段，除非未来产品确认机构端确实需要。

### 4.3 智能随访相关指标

建议作为单独摘要或服务项目子项展示：

1. AI 随访建议生成次数。
2. AI 建议转人工随访任务次数。
3. 智能随访任务生成次数。
4. 人工创建随访任务不计入 AI 用量。
5. AI 生成建议后由人工确认创建任务时，只按 AI 生成动作计量，不按人工确认动作重复计量。

当前若系统没有真实 usage 写入口径，不得宣称这些指标已经可统计，只能标记为后续能力。

### 4.4 低敏明细

如果第一版需要明细，建议只展示：

1. 时间。
2. 服务项目。
3. 状态。
4. 消耗额度。
5. 低敏错误状态，例如“已拒绝”“失败”“额度不足”。

默认不把明细作为第一刀必做，因为明细容易引发用户对账单、费用、失败原因和原始内容的误解。

## 5. 机构端默认不展示范围

机构端默认禁止展示：

1. provider。
2. model code。
3. Token 明细。
4. 平台 AI Credits 内部折算规则。
5. 真实成本。
6. RMB / `¥` / 人民币金额。
7. meteringDetails 原样 JSON。
8. metadata 原样 JSON。
9. prompt / question。
10. answer。
11. rawResponse。
12. apiKey / encryptedApiKey。
13. baseUrl。
14. Authorization / Cookie / Token 凭据。
15. 客户姓名、手机号、身份证、病历详情。
16. RAG source 原文。
17. 智能随访生成所依赖的原始治疗摘要或病历文本。
18. AI 随访建议原文，除非后续单独设计低敏展示和权限。
19. SQL、连接串、内部错误栈、供应商错误原文。

机构端不能直接复用平台端 DTO。即使平台端允许展示 provider/model/Token，机构端也应通过专用 facade 做字段白名单。

## 6. 关键产品口径选择

### 6.1 页面名称

推荐名称：`AI 服务额度`。

备选名称：`AI 服务使用`。

不推荐直接叫 `AI 用量与费用`，因为机构端不应看到费用和成本，也不应把页面理解为财务账单。

### 6.2 是否显示“AI 积分”

推荐：机构端默认不直接显示“AI 积分”，而是把平台端 AI Credits 转译为“AI 服务额度”。

原因：

1. “AI 积分”容易被理解为可购买积分、财务余额或结算凭证。
2. “AI 服务额度”更贴近套餐权益和使用限制。
3. 如果合同或套餐未来明确使用“AI 积分”，再单独调整文案。

### 6.3 是否显示 Token

推荐：不显示 Token。

Token 是平台计量和模型运营指标，不适合机构端普通运营人员理解。机构端只展示次数、额度和服务项目。

### 6.4 是否显示服务项目

推荐：显示服务项目，但使用产品化中文名。

服务项目是机构端最容易理解的维度，可以解释“额度消耗在哪里”，例如“知识库问答”“AI 问答”“治疗后随访建议”。

### 6.5 是否显示智能随访服务项目

推荐：显示，但必须区分真实可统计能力与后续能力。

若写入口径已经覆盖，展示“治疗后随访建议”“智能随访任务生成”等低敏聚合；若尚未覆盖，只在产品计划中保留，不在 UI 中宣称已完成。

### 6.6 是否显示明细记录

推荐：第一版可后置。

如确需展示，应只做低敏明细，不展示原始问答、随访建议正文、治疗摘要内容、provider、model、Token 或内部错误。

### 6.7 是否与套餐权益 / 配额联动

推荐：应联动，但分阶段。

第一版可以只展示使用量；当套餐权益系统能提供明确额度、周期、剩余额度和告警阈值时，再展示剩余额度和即将用尽提醒。

### 6.8 是否允许下载或导出

默认不做。

导出会放大字段泄露、误用为账单、权限扩散和客服解释成本。若未来要做，必须单独设计字段白名单、权限、审计和文件生命周期。

### 6.9 是否展示失败原因

默认只显示低敏状态，不显示内部错误。

建议状态：

1. 成功。
2. 已拒绝。
3. 额度不足。
4. 服务暂不可用。
5. 未计量。

不展示 provider 错误、HTTP 状态、SQL 错误、栈信息或原始拒绝文本。

### 6.10 智能随访计量边界

建议：

1. AI 生成建议算一次 AI 服务使用。
2. AI 生成随访任务草稿算一次 AI 服务使用。
3. 人工确认创建任务不重复计量 AI 用量。
4. 人工手动创建随访任务不计入 AI 用量。
5. AI 建议转人工确认可以作为转化指标，但不是额外 AI 用量。

## 8. 智能随访创建方式建议

### 8.1 人工创建随访任务

建议：

1. 不计入 AI 用量。
2. 进入普通随访业务统计。
3. 可记录随访任务创建、完成、逾期等业务指标。

### 8.2 AI 生成随访建议

建议：

1. 计入 AI 服务使用。
2. service project 可归类为 `follow_up_suggestion`。
3. 机构端展示为“治疗后随访建议”或“AI 随访建议生成”。
4. 不展示建议原文、治疗摘要原文、病历详情。

### 8.3 AI 生成随访任务草稿

建议：

1. 计入 AI 服务使用。
2. 需人工确认后才成为业务任务。
3. service project 可归类为 `follow_up_task_draft` 或与 `follow_up_suggestion` 合并展示。
4. 是否拆分枚举需后续写入口径阶段确认。

### 8.4 AI 建议转人工确认任务

建议：

1. 不重复计量 AI 用量。
2. 可作为转化指标展示，例如“建议转任务次数”。
3. 与“AI 服务额度消耗”分开表达。

### 8.5 自动随访策略生成

建议：

1. 作为后续能力。
2. 当前不宣称已完成。
3. 需要单独风控、权限、额度、审计和触达边界设计。

### 8.6 批量随访生成

建议：

1. 作为后续能力。
2. 需要单独额度策略和防误触机制。
3. 不得在当前机构端 AI 用量 V1 中顺手实现。

### 8.7 当前不可宣称边界

如果系统没有真实 usage 写入口径，不得宣称智能随访用量已经可统计。当前文档中的智能随访指标只是后续设计方向，不代表已完成能力。

## 9. 数据来源建议

后续机构端 facade 可基于：

1. `ai_call_usage_records`。
2. `tenantId` / `institutionId` 范围过滤。
3. service project 字段。
4. `meteringStatus`。
5. `aiCreditsConsumed`，但机构端转译为“AI 服务额度”。
6. follow-up / treatment summary / appointment 相关业务事件的低敏聚合。

数据读取边界：

1. 不读取 prompt / answer / rawResponse。
2. 不读取 metadata 原文。
3. 不读取 meteringDetails 原文。
4. 不暴露 provider / model / Token。
5. 不暴露客户姓名、手机号、身份证、病历详情。
6. 不把治疗摘要原文或随访建议原文作为用量统计字段。

## 10. API / facade 设计建议

本节只做设计，不实现。

后续建议新增机构端只读 facade，而不是复用平台端 AI usage DTO。

### 10.1 facade 目标

1. 从当前登录机构上下文获取 tenant / institution scope。
2. 返回机构端专用 DTO。
3. 只返回产品化字段。
4. 对平台内部字段做硬白名单过滤。
5. 支持时间范围。
6. 支持服务项目聚合。
7. 支持智能随访相关低敏聚合，但仅在写入口径完成后。

### 10.2 机构端 DTO 建议字段

建议字段：

1. `periodLabel`。
2. `totalServiceUses`。
3. `usedServiceQuota`。
4. `remainingServiceQuota`，可选。
5. `successRate`。
6. `byServiceProject`。
7. `trend`。
8. `followUpSummary`，可选。
9. `lowSensitiveDetails`，可选。

禁止字段：

1. provider。
2. model。
3. Token。
4. cost。
5. AI Credits 内部折算规则。
6. meteringDetails 原文。
7. metadata 原文。

### 10.3 明细是否支持

建议后续产品决策。

如果支持明细，应默认只展示低敏字段：

1. 时间。
2. 服务项目。
3. 状态。
4. 消耗额度。

不支持下钻到原始 prompt、answer、客户资料、治疗摘要或随访建议原文。

## 11. UI 设计建议

### 11.1 信息架构

### 11.2 文案原则

2. 不出现 Token / provider / model。
3. 用“AI 服务额度”替代内部计量术语。
4. 用“服务项目”解释用量去向。
5. 失败状态使用低敏中文。
6. 空状态文案建议：`暂无 AI 服务使用记录`。

### 11.3 额度提醒

接近额度提示作为后续能力。

建议文案方向：

1. `本月 AI 服务额度即将用尽，请联系平台管理员了解套餐权益。`
2. 不展示内部限制、模型限流、provider 错误或成本。

## 14. 风险与待确认问题

1. 机构端是否能理解“AI 积分”，还是必须统一转译为“AI 服务额度”。
2. AI 服务额度是否与套餐权益一致，是否已有合同或销售口径。
3. 没有套餐额度系统时，第一版是否只展示使用量。
4. 机构端是否需要明细，还是先只做聚合。
5. 失败 / 拒绝是否展示，展示到什么粒度。
6. 未归因服务是否展示，是否需要解释“历史记录未归因”。
7. 智能随访是否作为第一版服务项目展示。
8. 智能随访 AI 建议、任务草稿、人工确认的计量边界是否与运营口径一致。
9. 自动随访、运营辅助等未来服务项目如何进入机构端。
10. 是否会引发客户对费用、账单或扣费的误解。
11. 是否需要合同 / 套餐文案配合。
12. 是否需要操作员权限控制，例如只有机构管理员可看额度。
13. 是否需要先补智能随访真实 usage 写入口径，再做机构端 UI。
14. 是否允许机构端看到 `unknown / 未归因服务`，还是只在平台端治理。
15. 机构端额度提醒是否会引发续费或客服流程，需要平台侧运营配合。

## 15. 建议结论

建议机构端第一版采用“AI 服务额度 / AI 服务使用”产品口径，以服务项目、使用次数、成功率、已用额度和低敏趋势为核心，不展示平台内部模型、Token、成本、provider 或 AI Credits 折算规则。

智能随访应作为重要服务项目方向，但必须先区分 AI 生成动作和人工确认动作：AI 生成建议或任务草稿计入 AI 服务使用，人工确认和人工手动创建任务不重复计量。若当前写入口径未完成，不得在机构端宣称智能随访用量已可统计。
