# zmtg-pr-gatekeeper：PR 门禁规则

创建、更新、进入正式审查或合并 PR 时使用。授权和协作默认值以 [AGENTS.md](../../AGENTS.md) 及 [治理细则](../ai-agent-governance.md) 为准。

## 1. 基线与范围

- 从已验证的远端主线基线创建干净功能工作树；用户明确指定其他基线时记录。不要求用户的本地 `main` 与 `origin/main` 同步，不清理原目录已有改动。
- 核对当前分支、base、Head 和 `git status --short`；交付差异使用明确的 `git diff <base>...<head>`，不以提交后为空的 `git diff` 作为“没有改动”的证据。
- 一个 PR 只解决一个可独立验收的目标。通常保持 2–3 个文档或 3–5 个核心业务文件，测试和说明单列；超出时检查内聚性和拆分价值，不机械停工。
- 发现新增业务目标、未授权高风险操作或混入他人修改时，先暂停相关动作并处理范围问题。

## 2. 授权与 PR 状态

- 默认创建草稿（Draft）。进入正式审查（Ready）和合并（Merge）必须有覆盖当前 PR 的授权；同一会话已获授权时不重复询问。
- PR 状态与授权是两个事实，分别描述。不能因为 PR 仍为草稿就断言“尚未获得合并授权”。
- 状态以 `gh pr view` 或等效工具实际返回为准；转正式审查、合并后及时更新说明，不保留过期状态。
- 修改治理规则不自动授权该规则 PR 自行合并；用户对另一 PR 的合并授权不传递到本 PR。

状态示例按实际情况选择：

- 当前为草稿，尚未获得进入正式审查与合并的授权。
- 当前为草稿，已获准在必需检查与审查通过后进入正式审查并合并。
- 当前已进入正式审查，是否允许合并按已记录的用户授权判断。
- 当前已按授权合并，记录实际合并提交；部署状态另行说明。

## 3. 交付证据

PR 描述与实际内容必须一致：

1. 说明具体问题、变更后的行为及必要的兼容性信息。
2. 文件数与 `gh pr diff --name-only` 一致；核心代码、测试和文档分别统计，禁止遗漏越界文件。
3. 验证使用项目实际执行命令，不固定为某一种 runner。测试文件数、用例数、成功／失败／运行中状态均如实记录。
4. 同一提交及环境下的已有验证可引用复用；说明证据来源和局限，不冒称本轮重新执行。docs-only 不要求补跑无关 runtime 测试。
5. 写清任务排除项和未验证部分；runtime PR 包含风险与回滚方式。界面截图、模拟数据库或构建结果不能代替未执行的环境验收。
6. 标题与说明使用中文；技术原文保留。格式按复杂度组织，不必每次复制大段固定模板。

## 4. 合并门禁

只有当前授权包含合并时才执行：

1. 冻结实际 Head，确认 diff 仍在授权范围，相关发现已处理，验证证据对应当前版本。
2. 读取当前分支保护、必需检查、审查状态和冲突状态。检查运行中、失败、未知、存在未解决阻断或缺少所需审批时不合并。
3. 使用普通合并路径并匹配 Head，例如 `gh pr merge <number> --merge --match-head-commit <sha>`；合并方式遵守仓库策略。不得用 `--admin`、关闭保护或强推绕过门禁。
4. 读取合并结果，确认 `state=MERGED` 与实际合并提交，再更新 PR 说明。已获准的本地主线收口另检查原工作树是否可安全快进；未获准或有用户改动时保留原样。
5. Head 在过程中改变时重新核对差异与必需检查；原授权仍覆盖时无需重复索取，范围扩张则先处理新授权。

## 5. 简明回报

报告任务结果、PR 链接与实际状态、关键验证和剩余风险。审查或交接需要时补充 base／Head、文件数和保护检查证据。不得把“无代码冲突”写成“已获准合并”，也不得把“已提交／合并”写成“已部署”。
