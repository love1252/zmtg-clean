# AI-GOV-01：AI Agent 项目治理细则

> 更新日期：2026-10-05。适用于智美天工的任务授权、隔离协作、验证与交付。

日常默认规则见 [AGENTS.md](../AGENTS.md)。本文件说明边界与操作证据，不重复要求每轮加载全部历史文档。模型升级不改变用户权限、平台限制和项目保护规则。

## 1. 授权按结果判断，并在同一任务中沿用

| 用户要求 | 可自主完成 | 仍需核对的边界 |
|---|---|---|
| 分析、评估、比较、给建议 | 相关只读检查与结论 | 不自动实现或发布 |
| 修改文档或规则 | 必要 Markdown 修改、文档验证、提交与草稿 PR | 不夹带 runtime，不用新规则给本次任务补授权 |
| 实现／修复明确功能 | 必要源码、测试、说明、局部重构与现有分层接线；验证修正、提交、推送和草稿 PR | 用户排除项及高风险操作 |
| 审查或合并指定 PR | 按已获准的动作核查、修正交付说明、进入正式审查或合并 | 不把“审查”当“合并”；不绕过保护、不自动部署 |
| 批准明确列出的多步方案 | 依赖顺序内的已批准步骤，无需每步重复确认 | 未列出的后续任务和新增风险不在授权内 |

“可以”“按建议执行”“明确授权”等回复按紧邻上下文解析，只覆盖当时已说明的对象与动作，不外推为全部 backlog 的许可。用户的同一授权在后续轮次继续有效；事实变化影响范围时重新判断，不能把反复确认当作安全措施。

Codex 默认负责设计细化、实现、验证和交付，不要求用户在网页 ChatGPT 与 Codex 之间往返传递指令。用户可以指定其他工具或审查者；Claude Code 仅在被明确启用时使用。

完成边界应在任务开始时从请求中确定：结果、必要验收、交付形式、排除项。简单任务无需新建计划文件；复杂或跨步骤任务保留简短计划。没有正式任务编号可以自拟描述性标识，不编造历史阶段。

## 2. 风险边界与停止方式

`AGENTS.md` 列明的高风险操作必须有对应授权。授权应足以确定目标对象、允许动作和环境；例如“接入分页”不授权 Migration，“合并 PR”不授权生产部署，“修复配置读取”不授权读取真实密钥。

- 已授权的普通功能修改允许跨现有技术分层，不因同时涉及 route、DTO 和 repository 就视为跨业务域重构。
- 新增业务目标、改变数据所有权／权限／审计模型、破坏性数据操作、真实环境与财务后果仍需用户决定。
- 只读公开文档、Git／GitHub 开发协作与确认隔离的本地测试，按当前任务需要执行；真实业务数据与真实外部写入另核对授权。
- docs-only 和只读约束不能因“顺手修复”突破；计划中的实现细节不是 runtime 授权。工具所处的 Plan Mode 限制同样必须遵守。
- 修改治理规则本身不自动批准该规则 PR 的合并，也不追溯扩大当前任务授权；适用的授权仍来自用户会话。

遇到疑点先做安全的只读查证。只有目标仍不明、无法安全隔离、授权确实缺失、工具权限不足或会覆盖他人工作时，才暂停受影响动作。可以继续不依赖该决策的独立工作。说明实际证据、影响与最小可行选择，不对所有任务一律停工。

发现凭证暴露、未知真实环境或正在发生的写入冲突时，立即停止相关操作并报告，不继续探测敏感内容，不输出密钥或认证材料。

## 3. 启动事实与 Git 同步能力

开发前确认日期和时区、仓库路径、分支、HEAD、所用主线基线、工作树状态及当前授权范围。日期用 `date '+%Y-%m-%d %Z %z'` 或等价命令取得；同一任务的稳定事实可复用，提交和合并等关键动作前刷新相关状态。

需要提交、推送或 PR 时，在首次实质修改前实际验证下列交付路径之一：

- 普通 Git 路径：`git status --branch --short` 能读取状态；能在 `git rev-parse --git-dir` 指向的目录内创建并删除本任务临时探针，或已有同环境的成功 Git 写入证据；所需远端操作通过 `git fetch --dry-run origin` 或等价命令验证，GitHub CLI 具备本次 PR 操作能力。
- 完整连接器路径：核对实际工具、认证与仓库访问，确认支持本轮批量变更、创建 commit、更新 ref 和所需 PR 操作；不要求本地 `.git` 可写。只支持单文件 contents API 的连接器不能替代本轮多文件提交链路，不能仅凭“已安装”宣称可交付。

实际探针示例：

```bash
git status --branch --short
task_git_dir="$(git rev-parse --git-dir)"
task_probe="$task_git_dir/codex-write-probe-$$"
: > "$task_probe" && rm "$task_probe"
git fetch --dry-run origin
```

不要读取或输出真实业务凭证来证明 Git 可用。同一会话、同一仓库与权限环境中的成功证据可复用；换环境、权限变化或操作失败后再查。

能力不足时，先判断是否有获准且等效的工具路径。若无法完成约定交付，说明只能本地修改还是完全受阻，由用户选择交付调整，不在实现结束后才暴露同步限制。

## 4. 工作树与多 Agent 协作

- 新功能分支优先基于已验证的最新 `origin/main`。用户明确指定其他基线时记录原因；不强制改动用户的本地 `main` 来满足形式检查。
- 原目录已有不相关修改，记录后保留，在干净独立工作树中开发。不要自动 stash、checkout 覆盖、reset 或把这些修改收入本次提交。
- 当前任务分支中只允许本任务修改。出现来源不明的重叠改动时先暂停受影响写入；只读分析可继续。自身构建生成物先确认来源，再只清理本任务生成的内容。
- 同一工作树、分支、Git 索引只允许一个写入者。主 Agent 可委派并行只读调查、测试设计和独立复核。
- 需要并行实现时，每个写入 Agent 使用独立工作树和分支，明确文件归属、接口契约及验收；不能因目录不同就在同一工作树并发写入。
- 共用 Git 仓库的 worktree 管理、共享引用更新、合并与最终集成由主 Agent 串行执行；子 Agent 不操作其他分支或用户工作树。
- 合并子任务前核对其差异与验证结果，集成后验证组合行为。子 Agent 的结论不是测试或审查证据的替代品。

## 5. 按风险验证，复用可信证据

| 变更 | 本地验证重点 |
|---|---|
| 纯 Markdown 文档 | diff 范围、事实、内部链接、规则一致性、格式和无必要英文模板；不机械运行 runtime 全量测试 |
| 局部业务逻辑或查询 | 相关行为测试、边界与失败路径；按影响补类型检查和架构检查 |
| UI 和交互 | 用户可见行为、加载／空／错误状态、交互与实际渲染；涉及凭证才应用凭证输入专项断言 |
| 共享契约、权限或多模块行为 | 相关集成回归，必要时全量测试、类型检查和构建；验证范围说明风险依据 |
| 数据库、真实环境或部署 | 先核对精确授权和目标环境，再按专项门禁执行；模拟测试不能替代真实环境验收 |

优先使用项目脚本与仓库已有测试模式。测试应证明可观察行为、失败处理或安全边界，不为凑数量复述实现。不能通过删除断言、排除用例、放宽检查或伪造结果消除失败。

记录验证命令、目标提交（未提交时标明工作树）、结果、关键环境和局限。已通过结果在同一提交、相同依赖和相关环境未变化时可复用，不因回复一轮消息就重跑。修改后补相关验证；影响共享行为、出现新失败或证据不匹配时扩大范围。

本地验证与 GitHub 必需检查分别判断。复用本地或 CI 证据不能跳过当前 Head 要求的保护检查。不能把“已发起”“运行中”“模拟通过”表述为完整验收通过。

完整性判断以任务目标为准：接口通过不代表页面已接入，静态页面审计不代表提交流程可用，构建成功不代表已部署。

## 6. PR 范围、审查与合并

PR 必须单主题、可审查、可回滚。通常控制在 2–3 个文档文件或 3–5 个核心业务文件，相关测试和文档单列。单主题超出时先检查能否按独立行为拆分；紧密依赖且仍在授权内，可以说明原因继续。不能拆出不可用的半个功能来满足数量，也不能用“相关”掩盖新业务范围。

- docs-only PR 不得夹带 runtime；runtime PR 可包含同一功能必需的测试和说明。独立治理或规划调整另开 PR；schema／Migration 按独立授权处理。
- 默认交付草稿 PR。授权进入正式审查或合并后直接按 [PR 门禁](agent-guardrails/zmtg-pr-gatekeeper.md) 执行，不再次请求同一许可。
- 合并前冻结并核对 Head、实际 diff、检查结果、审查结论、分支保护及用户授权。Head 改变时先复核新差异和验证；目标或风险范围扩大才需要新授权。
- 使用支持匹配 Head 的合并操作，防止检查后版本被替换；不使用管理员绕过、强推主线或关闭保护规则来完成任务。
- 技术上可合并不等于用户已授权。Agent 独立复核也不能冒充 GitHub 所需的人类审批或绕过代码所有者要求。
- 合并后核验实际合并提交并更新 PR 状态说明；不自动部署、清理用户工作树或启动未批准的下一批。

## 7. 沟通、中文与文档维护

正常任务直接推进。进度聚焦实际发现、风险、决策和交付状态；不重复播报稳定的分支、日期或完整检查清单。需要用户决策时先完成能独立完成的工作，给出具体对象、推荐方案，以及哪条规则或事实导致暂停。

最终报告结果、验证、剩余风险与 PR 链接。详细命令和证据放在 PR 或任务确有需要的说明中，不强制每个任务生成 plan、devlog 和交接报告。

人读内容默认中文；Conventional Commit 前缀、技术标识、路径、API、固定契约、日志和历史直接引语保留原文。只处理任务涉及的文档，不为了中文化扩张范围。新建带日期的计划／devlog 使用命令所得日期；有必要追加当天记录时保留已有内容。`docs/superpowers/plans/` 与 `docs/superpowers/specs/` 的标题、模板字段和任务说明同样使用中文。

本次整理参考 [OpenAI 关于精简 Agent 指令的建议](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)：按任务加载相关规则，清楚定义完成边界，减少重复流程。该建议用于组织文档，不作为扩大权限或保证模型能力的依据。
