## 3. 目标

治疗项目路径模板 v1 的目标是让系统能够用更业务化、更稳定的方式描述“某类治疗项目在某个恢复阶段、某个风险等级下，应该建议什么随访动作，由谁处理，是否必须人工确认”。

具体目标：

- 从通用规则升级为可解释的项目路径模板。
- 支持首批常见医美项目路径：光子 / 光电治疗、水光 / 注射护理、术后修复、皮肤管理。
- 保持确定性和可测试，不引入 AI 自动生成建议。
- 保持结构化字段输入，不读取完整医疗正文。
- 输出仍然是内部随访任务建议，不是对客户的触达消息。
- 所有建议都必须人工确认。
- 所有模板都明确禁止自动触达。
- 继续使用来源字段追踪治疗摘要和建议 key。
- 为后续机构 SOP、路径分析和经营智能打基础，但当前不实现这些能力。

## 4. 和现有能力的关系

### 4.1 和治疗摘要的关系

治疗摘要仍是当前路径模板的主要输入。路径模板 v1 只应读取现有安全结构化字段：

| 输入字段 | 当前用途 | Phase 20 模板规划中的用途 |
| --- | --- | --- |
| `treatmentProject` | 展示治疗项目名称 | 可作为项目类型辅助识别，但不能承载完整治疗正文。 |
| `treatmentCategory` | 确定性类别规则输入 | 优先作为项目类型匹配依据。 |
| `treatmentStage` | 展示治疗阶段 | 辅助识别治疗中、复诊前、术后护理等阶段。 |
| `recoveryStage` | 确定恢复期 | 映射 D0 / D1 / D3 / D7 / D14 / 稳定期等恢复阶段。 |
| `riskLevel` | 影响建议优先级 | 决定随访节点提前、升级或人工角色调整。 |
| `nextCareAction` | 可转为下一步护理建议 | 继续作为人工任务建议的补充描述。 |
| `tags` | 展示标签 | 可辅助识别项目和风险，但不能覆盖字段白名单。 |
| `status` | active / voided | voided 摘要不能生成新路径建议或新来源任务。 |

路径模板 v1 不改变治疗摘要 schema，不新增完整治疗记录字段，不保存完整病历正文，不保存咨询全文。

### 4.2 和当前确定性随访建议的关系

当前 `buildTreatmentFollowUpSuggestions` 已经能根据风险、恢复早期、下一步护理动作和类别规则生成确定性建议。

Phase 20 的规划方向是：

- 将现有“风险规则 + 恢复早期规则 + nextCareAction 规则 + 类别规则”整理为更清晰的模板模型。
- 让类别规则从“单条提醒”升级为“项目类型 + 恢复阶段 + 风险等级 + 随访节点”的组合。
- 保留稳定 `suggestionKey` 作为来源追踪基础。
- 保留建议 DTO 的安全字段边界。
- 保留“建议只读 API 不写数据库、不创建任务”的边界。
- 保留“人工确认后才创建内部随访任务”的边界。

后续如果改动 `suggestionKey` 结构，必须单独评估兼容性，因为现有来源任务依赖 `sourceSuggestionKey` 做重复创建治理。

### 4.3 和来源随访任务的关系

来源随访任务仍然是模板建议转行动的承接点。

当前任务来源字段：

- `source: "treatment_summary"`
- `sourceTreatmentSummaryId`
- `sourceSuggestionKey`

Phase 20 规划后，路径模板建议仍应沿用这些来源字段。可以在后续实现中考虑让 `suggestionKey` 体现模板 key、恢复阶段和节点 key，但 v1 不应新增数据库字段来保存模板原文。

来源任务继续遵守：

- 人工确认后才创建。
- 同租户内同来源活跃任务去重。
- 任务创建后进入智能随访。
- 既有任务不因治疗摘要编辑或作废被自动取消。
- 作废摘要阻断新建议和新任务。
- 任务不自动发微信、短信、电话或企业微信。

## 5. 首批建议支持项目类型

Phase 20 v1 首批建议只覆盖高频、可演示、规则相对稳定的项目类型。

| 项目类型 | 建议内部 key | 当前可映射来源 | v1 目标 |
| --- | --- | --- | --- |
| 光子 / 光电治疗 | `photoelectric_care` | `treatmentCategory=laser_repair`，或安全项目名包含光子、光电、热玛吉等后续可评估词 | 关注泛红、补水、防晒、屏障修复和 D1 / D3 / D7 节点。 |
| 水光 / 注射护理 | `hydro_injection_care` | `treatmentCategory=injection_review`，或安全项目名包含水光、注射、填充等后续可评估词 | 关注局部反应、针眼护理、恢复反馈、复诊和续疗窗口。 |
| 术后修复 | `post_surgery_repair` | `treatmentCategory=skin_repair`，或安全阶段 / 标签包含术后、修复、复查等后续可评估词 | 关注高风险恢复期、异常反馈、复查安排和医助 / 护理人员介入。 |
| 皮肤管理 | `skin_management` | `treatmentCategory=skin_check`，或安全项目名包含皮肤检测、补水护理、皮肤管理等后续可评估词 | 关注检测后解释、护理建议理解、复购 / 复诊提醒和稳定期维护。 |

v1 不建议一次性覆盖所有项目。抗衰疗程、私密、植发、牙科、复杂手术、联合项目和机构自定义 SOP 应后续单独评估。

## 6. 路径模板建议字段

路径模板 v1 建议使用概念模型，不在本 PR 落库。

模板建议至少包含：

| 字段 | 说明 |
| --- | --- |
| 项目类型 | 如光子 / 光电治疗、水光 / 注射护理、术后修复、皮肤管理。 |
| 恢复阶段 | 如 D0、D1、D3、D7、D14、复诊前、稳定期。 |
| 风险等级 | 复用现有 `normal`、`watch`、`urgent`。 |
| 建议随访节点 | 建议何时人工跟进，例如治疗后 1 天、3 天、7 天。 |
| 建议任务标题 | 展示给员工的内部任务标题，例如“光电术后 D3 护理确认”。 |
| 建议处理角色 | 建议由客服、咨询师、医助、护理人员或运营负责人处理。 |
| 是否需要人工确认 | v1 必须为 `true`，不允许自动创建任务。 |
| 禁止自动触达 | v1 必须为 `true`，不允许自动发微信、短信、电话或企业微信。 |

可选但建议后续实现时考虑的辅助字段：

| 字段 | 说明 |
| --- | --- |
| 模板 key | 稳定内部 key，用于测试和建议 key 生成。 |
| 节点 key | 稳定节点 key，例如 `d1_care_check`、`d7_recovery_review`。 |
| 优先级 | 可从风险等级和恢复阶段派生，不一定需要模板显式维护。 |
| 来源字段 | 记录该建议由哪些结构化字段触发。 |
| 安全说明 | 标记不读取完整正文、不自动触达、不替代医疗判断。 |

概念示例：

```text
项目类型：光子 / 光电治疗
恢复阶段：D3
风险等级：watch
建议随访节点：治疗后第 3 天
建议任务标题：光电术后 D3 护理确认
建议处理角色：客服或医助
是否需要人工确认：是
禁止自动触达：是
```

该示例只是产品规划，不代表当前已经存在模板配置或数据库记录。

## 8. 匹配策略建议

后续如进入实现，建议采用保守匹配顺序：

1. 优先使用 `treatmentCategory` 的稳定枚举或白名单 key。
2. 再使用 `recoveryStage` 和 `treatmentStage` 判断恢复阶段。
3. 再使用 `riskLevel` 调整节点时点、优先级和建议处理角色。
4. `nextCareAction` 只作为安全短文本补充，不覆盖模板的人工确认和禁止自动触达边界。
5. `treatmentProject` 和 `tags` 只用于安全辅助匹配，必须经过敏感字段拦截和白名单规范化。
6. 匹配不清晰时使用轻量默认随访建议，不要猜测高风险项目。

模板匹配必须确定性、可测试、可解释。不能调用 AI、不能请求外部系统、不能读取外部 raw payload。

## 9. 不落库边界

Phase 20 v1 的路径模板不落库。PR #95 只规划；后续 PR 已采用 domain-only 静态 catalog 完成最小实现，仍未新增模板表、模板 API 或路径实例表。

后续如果进入最小实现，优先考虑代码内静态模板 catalog 或 domain-only 模型，原因：

- 当前首批模板数量有限。
- 当前尚未确认机构自定义 SOP 的配置需求。
- 当前还没有路径版本、启停、审批、灰度、租户级覆盖和审计需求。
- 过早落库会引入 schema、API、权限、后台配置和版本治理风险。

必须单独评估 schema / API 的情况：

- 机构需要自定义或编辑路径模板。
- 平台需要配置不同套餐可用模板。
- 路径模板需要启停、版本、审批或变更审计。
- 需要记录客户进入路径的实例状态。
- 需要做路径效果分析、漏斗和归因。
- 需要给外部系统或客服工作台暴露模板 API。

上述任一情况都不属于当前 docs-only PR，也不应直接混入 Phase 20 v1 最小实现。

## 10. HIS / 企微 / AI 边界

### 10.1 HIS 边界

Phase 20 不接真实 HIS，不新增 Webhook，不做文件导入，不保存 HIS raw payload。

未来 HIS 标准治疗事件可以成为治疗摘要或路径模板匹配的上游来源，但必须经过 Phase 17 已定义的标准治疗事件模型和字段白名单。外部 `tenantId` 不可信，外部原文不进入路径模板。

### 10.2 企业微信和自动触达边界

Phase 20 不接企业微信，不接个人微信，不发短信，不电话外呼。

路径模板只产生内部随访建议或内部任务建议。即使未来存在任务标题或建议动作，也不能被解释为客户消息模板。任何企业微信、短信、电话、客服工作台触达能力都必须单独 Plan Mode，评估授权、模板、频控、退订、审计和合规。

### 10.3 AI 边界

Phase 20 不接 AI provider，不做 RAG，不做 Agent，不用 AI 生成护理建议。

路径模板 v1 必须基于机构可解释 SOP 和结构化字段，以确定性规则输出。未来如需要 AI draft，也必须是独立阶段，并继续要求人工确认，不自动触达。

## 11. 隐私和安全边界

路径模板和建议生成禁止读取、保存、展示或传播：

- 完整治疗记录正文。
- 完整病历正文。
- 诊疗原文。
- 咨询对话全文。
- 手机号原文。
- 身份证号。
- 病历号原文。
- 图片 / 文件原文。
- 外部系统 raw payload。
- AI 生成医疗建议原文。
- SQL、stack、token、secret、`DATABASE_URL` 或连接串。

所有后续实现都必须继续遵守：

- 服务端从 access context 推导 `tenantId`。
- 前端不能传入或切换 `tenantId`。
- DTO 白名单。
- payload 白名单。
- 租户隔离。
- 人工确认。
- 来源可追踪。
- 作废摘要不再生成新建议或新任务。
- 不自动触达。
