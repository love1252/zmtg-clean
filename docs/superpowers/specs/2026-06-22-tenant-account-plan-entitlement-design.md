# 平台端租户管理、账户开设与套餐授权设计方案

> 状态：docs-only 设计方案。日期来自本地命令 `date "+%Y-%m-%d"`，结果为 2026-06-22；时区为 CST +0800。
>
> 本文只规划平台端租户管理、账户开设、套餐选择、授权快照、查询与审计入口的产品和技术边界，不实现 runtime，不修改 `src/**`、数据库 schema、migration、SQL、真实 API、支付、计费、外部系统或凭证。

## 1. 任务目标

平台端租户管理需要从当前“只读查看机构、套餐和配额边界”的状态，演进为可支撑测试使用的租户管理工作台。它不只是“新建租户”入口，而是平台侧查看、开设、解释授权、定位风险和追溯审计的统一栏目：

- 所有租户账户必须由平台管理端开设。
- 开设租户时必须选择产品套餐。
- 不同套餐对应不同功能权限、容量配额、AI 用量边界和可见模块。
- 租户开设、套餐分配、启用、停用、变更和过期都必须可审计。
- V1.1 先覆盖租户概览、查询列表、新建租户、授权快照和审计入口，不做公开自助注册、不做真实支付、不做发票合同、不做自动营销触达。

- `src/modules/security/domain/access-control.ts`：已有平台角色、租户角色、受保护资源和动作的基础访问控制。

当前缺口：

- 租户管理仍以查看为主，没有账户开设工作流。
- 套餐权益只是只读词汇，没有成为租户权限计算的正式来源。
- 还没有“套餐 -> 权益 -> 配额 -> 租户授权 -> 账号初始角色”的闭环。
- 租户开设、套餐变更和权限变更的审计策略需要先定义。

## 3. GitHub 旧系统参考结论

已只读检查 GitHub 旧项目 `love1252/zmtg`，参考提交为 `b8b398b 更新了部分丢失的AI厂商logo`。重点参考文件：

- `/tmp/zmtg-old-readonly/src/components/pages/OpenPlatform.tsx`
- `/tmp/zmtg-old-readonly/src/app/api/v1/platform/tenants/route.ts`
- `/tmp/zmtg-old-readonly/src/app/api/v1/tenants/[id]/route.ts`

旧系统里的“租户管理”不是单纯的新建表单，而是一个较重的平台管理模块，包含：

- 租户总览：机构总数、正常机构、冻结机构、企微身份席位、月经常收入。
- 开通入口：页面右上角有“开通新租户”主按钮。
- 开通向导：包含机构名称、负责人、套餐、员工席位、企微身份席位、Agent 数量、客户档案、月 API 调用等字段。
- 套餐权益校验：选择套餐后展示配额校验结果。
- 租户列表：支持搜索机构名称或编码，并按套餐、状态筛选。
- 租户详情：展示联系人、员工席位、企微身份席位、客户档案、月费等信息。
- 后端工作流：平台租户接口同时返回租户、审计日志、订单、合同、开票资料、支付事件和用量费用。

旧系统可吸收的设计经验：

- 租户管理栏目需要先解决“整体查询和运营判断”，不能只做“新建租户”。
- 新建租户必须和套餐绑定，并在提交前解释配额与功能边界。
- 详情页需要展示当前租户的套餐、授权、配额和风险状态。
- 开设、套餐分配和后续关键变更都应该进入审计。

旧系统不建议照搬的部分：

- 不复制巨型 `OpenPlatform.tsx` 的实现方式，后续 runtime 应保持模块边界清晰。
- 不在 V1.1 混入真实计费、合同、发票、支付事件和商业收入。
- 不在 V1.1 做明文密码、重置密码、删除租户等高风险能力。
- 不复用依赖前端 header 或 localStorage 的租户边界做法。
- 不把“套餐权益”直接等同于“角色权限”。

基于旧系统，本文将原方案从“租户开设流程”升级为“租户管理栏目 V1.1”：先做租户概览、查询列表、新建租户、授权快照和审计入口，后续再拆分套餐变更、冻结恢复、配额覆盖、计费合同等任务。

## 4. 外部参考

本方案参考以下公开资料，只吸收产品和架构模式，不引入第三方服务依赖：

- Stripe Billing Entitlements：Stripe 将产品功能映射为 Entitlements，并建议在客户访问服务时使用 active entitlements 判断是否授予功能访问。参考：https://docs.stripe.com/billing/entitlements 和 https://docs.stripe.com/billing/subscriptions/overview
- Stripe Usage-based pricing：用量型订阅需要记录周期内用量，并可按 usage records 或 meter 口径汇总。参考：https://docs.stripe.com/subscriptions/pricing-models/usage-based-pricing
- Chargebee Entitlements：Entitlement 连接 feature 与 item 或 item price，用于说明某个套餐/价格项拥有的功能范围；订阅上还可出现覆盖项。参考：https://www.chargebee.com/docs/billing/2.0/entitlements/entitlements 和 https://apidocs.chargebee.com/docs/api/entitlements
- Chargebee Feature Management：套餐、附加项和费用项可以解锁功能，功能管理和版本管理需要独立。参考：https://www.chargebee.com/docs/billing/2.0/entitlements/feature-management
- Microsoft Entra 多租户用户生命周期：多租户环境需要统一用户生命周期、租户边界、跨租户同步和访问控制。参考：https://learn.microsoft.com/en-us/entra/architecture/multi-tenant-user-management-scenarios

对本项目的结论：

- 套餐不应直接等同于角色。套餐负责“能力和容量”，角色负责“人在租户内能做什么”。
- 租户开设应是平台端受控流程，完成后生成租户、初始管理员、套餐权益快照和审计记录。
- 权益应结构化，不应只靠页面文案判断。
- 套餐权益需要支持版本化，否则未来套餐改版会影响历史租户解释。

## 5. 推荐设计路线

推荐采用“套餐模板 + 权益版本 + 租户授权快照 + 角色权限”的四层模型。

### 5.1 套餐模板

套餐模板定义平台可售卖或可分配的标准方案，例如：

- 试用版
- 基础版
- 专业版
- 旗舰版
- 定制版

套餐模板只表达产品侧能力组合，不直接绑定具体机构。每个套餐应包含：

- 套餐编码：稳定唯一，例如 `trial`、`basic`、`professional`、`enterprise`、`custom`。
- 套餐名称：用于平台端和内部运营展示。
- 套餐状态：草稿、启用、停用、归档。
- 生效版本：指向当前权益版本。
- 适用边界：是否允许新租户选择、是否仅内部可见、是否需要审批。

### 5.2 权益版本

权益版本是套餐在某个时间点的能力清单。示例权益维度：

| 维度 | 示例 | 说明 |
| --- | --- | --- |
| 模块可见性 | 客户管理、治疗摘要、知识库、AI 助手、开放连接 | 控制租户是否拥有模块入口 |
| 功能门禁 | 客户管理模块、治疗摘要模块、知识库导入、AI 对话 | 控制租户是否拥有该能力入口 |
| 容量配额 | 客户数、预约数、随访任务数、知识库文件数、AI 调用次数 | 控制资源上限 |
| AI 能力 | 可用模型、每日调用上限、月度调用上限、单次 Token 上限 | 控制模型与费用边界 |
| 数据能力 | 导出、报表、审计查看、保留周期 | 控制数据访问和留存 |
| 服务等级 | 是否允许人工配置、是否允许试运行、是否允许企业定制 | 控制运营服务边界 |

权益版本必须可审计、可回溯。新版本只影响之后新开设或主动变更的租户；历史租户保留其开设时的权益快照，除非平台执行套餐变更。

### 5.3 租户授权快照

租户开设成功后，应生成一份“租户授权快照”。该快照由套餐权益版本计算而来，并可叠加平台审批后的租户级覆盖项。

快照建议包含：

- `tenantId`
- `planCode`
- `planVersion`
- `assignmentStatus`
- `effectiveFrom`
- `expiresAt`
- `enabledModules`
- `enabledActions`
- `quotaLimits`
- `aiModelPolicy`
- `overrides`
- `snapshotReason`
- `createdBy`
- `createdAt`

快照是运行时权限和配额判断的输入之一，但不替代 RBAC。它回答“这个租户买了/被分配了什么能力”；RBAC 回答“当前用户在这个租户里是否能执行这个动作”。功能门禁是租户级开关，不应直接改写 `ACCESS_ACTIONS` 或角色策略。

### 5.4 角色权限

角色权限保持独立：

- 平台管理员：开设租户、分配套餐、调整授权、查看审计。
- 平台运营：查看租户、发起开设申请、查看套餐分配，是否能提交开设需按审批策略确认。
- 租户管理员：管理本租户用户、查看本租户授权和用量，不可越权修改套餐。
- 租户运营/咨询/客服：只能使用租户已开通且其角色允许的功能。

最终授权判断建议为：

```text
是否允许 = 租户状态有效
        && 套餐授权快照包含该模块/能力
        && 当前用户角色具备该动作
        && 配额没有触发阻断
        && 功能开关或灰度策略允许
```

## 6. 平台端租户开设流程

V1.1 建议采用平台端受控表单 + 审核确认页，不做多步骤复杂审批流。

### 6.1 开设入口

在“租户管理”页面增加主操作：

- 新建租户
- 查看开设记录
- 查看套餐授权快照

入口需要清楚标注：

- 仅平台管理员可提交。
- 测试环境允许开设测试租户。
- 开设后会创建租户、初始管理员账号和套餐授权快照。

### 6.2 表单字段

V1.1 最小字段：

| 分组 | 字段 | 说明 |
| --- | --- | --- |
| 机构信息 | 机构名称 | 必填 |
| 机构信息 | 机构简称 | 可选，用于列表展示 |
| 机构信息 | 联系人姓名 | 必填 |
| 机构信息 | 联系人手机号 | 必填，需脱敏展示 |
| 机构信息 | 联系人邮箱 | 可选 |
| 初始账号 | 管理员姓名 | 必填 |
| 初始账号 | 管理员手机号或邮箱 | 至少一个 |
| 初始账号 | 初始角色 | 默认租户管理员 |
| 套餐选择 | 套餐 | 必填 |
| 套餐选择 | 有效期 | 必填，试用版可默认 14 或 30 天 |
| 套餐选择 | 权益预览 | 自动展示 |
| 安全确认 | 创建原因 | 必填，进入审计 |

V1.1 不建议把合同金额、发票、付款状态、销售人员提成等纳入表单，避免把租户开设和真实计费混在一起。

手机号、邮箱等字段属于 PII。进入 Phase C runtime 前必须单独审批收集、存储、脱敏、审计和保留策略。当前方案只定义字段存在性，不定义存储实现。

### 6.3 套餐选择交互

选择套餐后页面应展示：

- 开通模块列表。
- 核心操作权限摘要。
- 配额上限。
- AI 模型与调用边界。
- 过期后的行为。
- 是否允许租户自助邀请成员。

如果选择“定制版”，需要显示“需平台审批/需人工复核”的提示。V1.1 可先不做审批工作流，但必须在方案里保留状态。

### 6.4 提交前确认

提交前显示确认页：

- 将创建哪个租户。
- 将创建哪个初始管理员。
- 分配哪个套餐和版本。
- 授予哪些模块、动作和配额。
- 哪些字段会写入审计。

确认页要避免展示完整敏感信息，例如手机号只展示脱敏版本。

### 6.5 成功后状态

成功后租户进入：

- `active`：可登录和使用。
- `trialing`：试用租户，可登录但受试用权益限制。
- `pending_activation`：预留状态，适合未来需要人工确认初始账号通知的场景。

V1.1 推荐默认 `active` 或 `trialing`，不要引入复杂审批。`pending_activation` 在短信、邮件或其他通知能力经单独任务审批并实现之前，不触发实际流转。

## 7. 套餐与权限关系

### 7.1 推荐的套餐层级

| 套餐 | 适用对象 | 核心能力 | 建议边界 |
| --- | --- | --- | --- |
| 试用版 | 新机构试用 | 基础客户管理、有限 AI、有限知识库 | 有效期短、配额低、不可导出 |
| 基础版 | 小型机构 | 客户旅程、治疗摘要、基础随访 | AI 和知识库容量有限 |
| 专业版 | 成长期机构 | 更多 AI、知识库、运营看板 | 开放更多报表和协作能力 |
| 旗舰版 | 多团队机构 | 高容量、更多模型、审计增强 | 可启用更高配额和更多管理员 |
| 定制版 | 大客户 | 按合同配置 | 必须人工审批和审计 |

### 7.2 权益维度建议

V1.1 不要把所有页面都做成套餐权限。建议先覆盖会影响真实使用边界的能力：

- 客户与预约容量。
- 治疗摘要和随访能力。
- 知识库条目、文件、上传、解析、检索。
- AI 模型可用范围、调用次数、Token 或费用上限。
- 数据导出。
- 成员数量。
- 审计可见范围。

暂不纳入 V1.1：

- 合同、支付、发票。
- 自动营销发送。
- 外部 HIS 真实连接。
- 高级 BI 收入分析。
- 复杂审批流。

### 7.3 覆盖项

需要支持租户级覆盖项，但必须受控：

- 增加某项配额。
- 临时延长试用期。
- 开启某个试验能力。
- 临时关闭某个高风险能力。

覆盖项必须包含：

- 覆盖原因。
- 操作人。
- 生效时间和失效时间。
- 审计记录。
- 是否可被下次套餐变更覆盖。

## 8. 页面与信息架构建议

### 8.1 租户管理栏目

建议拆成五块，形成“先看全局、再查租户、再看详情、再开设新租户、最后追溯审计”的管理路径：

1. 租户概览：全部租户、运行中、试用中、即将到期、授权异常或套餐缺失。
2. 租户查询与列表：机构、租户 ID、状态、套餐、有效期、授权快照状态、配额风险、最近更新。
3. 新建租户：平台管理员通过三步流程开设租户，选择套餐并确认授权快照。
4. 租户详情与授权快照：基础信息、当前套餐、授权快照、用量摘要、风险提示、审计入口。
5. 审计与后续操作入口：跳转平台审计日志，后续再开放套餐变更、延长试用、冻结恢复和配额覆盖。

V1.1 建议优先把“概览 + 查询列表 + 详情快照 + 新建租户三步流程”作为完整设计对象。真正进入 runtime 时仍可分阶段实现，但效果图和交互方案必须先解释完整租户管理路径，避免栏目看起来只有一个新建入口。

### 8.2 租户概览

概览用于回答“当前平台有哪些租户状态需要关注”，不做商业化收入大屏。推荐指标：

- 全部租户：当前平台可见租户数量。
- 运行中租户：状态为 `active` 的租户。
- 试用中租户：状态为 `trialing` 的租户。
- 即将到期：有效期进入预警窗口的租户。
- 授权异常：缺少套餐、快照失效、配额缺失或关键授权不完整的租户。

不建议在 V1.1 概览中展示月经常收入、付款状态、合同状态或开票状态。这些属于商业化、计费或合同模块，应在后续任务单独设计。

### 8.3 租户查询与列表

列表是租户管理的主工作区，字段应服务于运营查询和授权判断：

| 字段 | 说明 |
| --- | --- |
| 机构名称 | 平台运营识别对象 |
| 租户 ID / 编码 | 稳定定位租户 |
| 租户状态 | `trialing`、`active`、`suspended`、`expired` 等 |
| 当前套餐 | 当前生效套餐名称和版本 |
| 套餐有效期 | 展示开始、到期或剩余天数 |
| 授权快照状态 | 正常、待生成、已过期、存在覆盖项 |
| 配额风险 | 低风险、接近上限、已阻断、缺少上限 |
| 最近更新 | 最近一次租户或授权变更时间 |
| 操作 | 查看、审计入口，其他高风险操作先禁用或后置 |

筛选建议：

- 关键词：机构名称、租户 ID、编码。
- 状态：全部、运行中、试用中、冻结、过期。
- 套餐：全部、试用版、基础版、专业版、旗舰版、定制版。
- 有效期：全部、即将到期、已过期。
- 授权状态：正常、异常、有覆盖项。
- 配额风险：全部、接近上限、已阻断、缺少上限。

### 8.4 租户详情与授权快照

租户详情应承接列表中的“查看”动作，推荐右侧抽屉或独立详情页。V1.1 重点展示：

- 基础信息：机构名称、租户 ID、租户状态、创建时间、最近更新。
- 当前套餐：套餐名称、套餐版本、有效期、分配状态。
- 授权快照：已开通模块、功能门禁、配额上限、AI 用量边界、知识库边界。
- 当前用量摘要：客户数、成员数、知识库文件、AI 调用、关键配额使用率。
- 风险提示：即将到期、套餐缺失、快照失效、配额缺失、已触发阻断。
- 审计入口：跳转到平台审计日志，并带上租户 ID 作为筛选条件。

详情页只解释当前租户“拥有什么能力、用了多少、哪里有风险”。V1.1 不在详情页内直接修改套餐、重置密码、删除租户或调整配额。

### 8.5 新建租户路径

新建租户仍采用三步流程：

1. 机构与初始管理员：录入机构名称、简称、联系人、初始管理员。手机号和邮箱属于 PII，后续 runtime 前必须单独审批存储、脱敏和保留策略。
2. 套餐与权益预览：选择套餐，展示功能门禁、容量配额、AI 用量边界、知识库能力和成员上限。
3. 提交确认：展示将创建的租户、初始管理员、套餐版本、有效期、授权快照和审计摘要。

提交成功后进入租户详情或回到列表，并能看到新租户的授权快照状态。失败时必须说明是否已写入租户或快照，不展示服务端内部错误。

### 8.6 产品与套餐栏目

建议承担套餐模板和权益版本的管理视图：

- 套餐列表。
- 权益矩阵。
- 配额表。
- 版本历史。
- 哪些租户正在使用该版本。

V1.1 可以先只做只读或轻量配置，不要一次性做完整商业化后台。

### 8.7 权限与审计关系

“平台审计日志”需要记录：

- 租户创建。
- 初始管理员创建。
- 套餐分配。
- 套餐变更。
- 权益覆盖项创建/失效。
- 租户停用/恢复。
- 配额阻断。

审计展示必须使用中文业务词汇，不展示请求体、凭证、原始错误、SQL 或内部 stack。

## 9. 数据与状态模型建议

### 9.1 核心实体

| 实体 | 用途 |
| --- | --- |
| Tenant | 租户主体 |
| TenantAccount | 初始管理员和租户用户账号 |

## 10. 安全与合规边界

- 平台端创建租户必须要求平台身份，不接受前端传入任意 `tenantId` 作为可信边界。
- 初始管理员账号必须有安全初始化流程，不能明文展示或记录密码。
- 手机号、邮箱、联系人等字段在列表和审计中应脱敏。
- 套餐权限不能绕过角色权限。
- 配额阻断不能只在前端做，后续必须在服务端关键动作处校验。
- 审计事件只记录低敏摘要和必要 ID，不记录完整请求体。
- 测试环境和生产环境的租户开设策略必须可区分。

## 11. 分阶段落地建议

### Phase A：方案与契约确认

只做 docs/spec，不改 runtime：

- 明确租户开设流程。
- 明确套餐权益矩阵。
- 明确审计事件。
- 明确哪些字段进入 V1.1。

### Phase B：只读契约和测试

不开放创建能力，先建立 domain-only 契约：

- 套餐权益类型。
- 授权快照计算函数。
- 权益与角色合并判断函数。
- 单元测试覆盖套餐差异、覆盖项、过期、配额阻断。

### Phase C：平台端租户开设 V1.1

受控 runtime：

- 平台端新建租户表单。
- 服务端创建租户、初始管理员、套餐分配、授权快照。
- 审计记录。
- 不接支付、不接外部系统。

### Phase D：套餐管理 V1

受控 runtime：

- 套餐模板和权益版本管理。
- 版本生效策略。
- 租户套餐变更。
- 覆盖项管理。

### Phase E：真实用量和配额 enforcement

单独任务：

- 将客户、知识库、AI 调用等关键动作接入配额校验。
- 形成用量快照。
- 处理超额提示和审计。

## 12. 推荐 V1.1 范围

V1.1 建议只做：

- 平台管理员创建租户。
- 创建一个初始租户管理员。
- 创建时选择套餐。
- 根据套餐生成授权快照。
- 租户列表展示套餐、有效期、状态、配额摘要。
- 租户详情展示授权快照。
- 审计记录租户创建和套餐分配。

V1.1 不做：

- 真实计费、支付、合同、发票。
- 公开注册。
- 复杂审批流。
- 自动创建外部 HIS 连接。
- 自动营销触达。
- 任意跨租户数据迁移。
- 真实生产套餐售卖。

## 16. 当前结论

平台端租户管理可以从“演示只读”演进到“受控开设租户”，但必须先把套餐权益结构化。最稳妥的路线不是直接在页面上加创建按钮，而是先建立“套餐模板、权益版本、租户授权快照、角色权限”的边界。这样未来无论是试用租户、正式租户、定制租户，还是 AI 用量、知识库容量、客户数量限制，都能在同一套授权模型下解释和审计。
