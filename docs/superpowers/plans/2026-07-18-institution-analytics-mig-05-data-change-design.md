# MIG-05：机构经营分析消费事实数据变更设计申请

**任务：** `AN-02 / MIG-05-DESIGN`

**状态：** 仅设计申请；不构成 schema、Drizzle、migration、导入或外部集成实施授权。
**申请所有者：** 经营分析线提出业务事实与验收要求；总协调台拥有唯一 migration 编排、公共声明与最终落地决定。

## 一、申请结论与串行位置

申请将下列消费事实基础纳入唯一 `MIG-05` 数据变更单元：消费来源、受控导入批次及行、稳定业务消费单、成功支付、确认退款、客户匹配、HIS 标准项目映射、幂等与追加纠正。

唯一顺序不可改写：

```text
MIG-01 → MIG-02 → MIG-03 → MIG-04 → MIG-05 → MIG-06
```

`MIG-05` 必须在 `MIG-01` 至 `MIG-04` 已合并、其机构归属与客户稳定引用前提可用后才可进入 migration 队列；同一时间只能有一个 migration PR。`MIG-06` 的分析 snapshot、报告输入/输出、版本、归档和来源变化状态不在本申请内，不能提前建表或回填。

本申请不实现 HIS、ERP、POS adapter，不执行受控导入，不接外部网络、凭证、worker、scheduler、API 或页面。上述外部能力均进入总协调台唯一串行外部集成交付队列；本线只提出其规范化事实的验收条件。

## 二、权威事实、范围与不接受的替代物

机构经营金额只来自经验证的业务消费来源中的 `payment_succeeded` 与 `refund_confirmed` 事实。治疗摘要、平台商业记录、演示数据、页面提交、支付笔数、项目行数或数据库行数都不能冒充消费事实或稳定业务消费单。

| 事实类别 | 最小业务含义 | 计入规则 | 明确不替代 |
| --- | --- | --- | --- |
| 消费来源 | 一项获准来源配置及其来源类型、连接/批次边界、状态和高水位 | 仅持久化已通过来源治理的规范化结果 | 页面刷新、未获准 adapter、模拟连接 |
| 导入批次与行 | 受控导入预检批准后产生的不可变批次摘要及逐行规范化/拒绝结果 | 合法行可进入事实链；非法行保留低敏失败原因而不伪造成功 | 原始文件、自由文本、文件内容或外部账号 |
| 稳定业务消费单 | 机构内安全、可审计且跨重放稳定的业务消费单引用 | 仅其可靠性已确认时可计算消费单数、次数、明细和记录详情 | 支付号、退款号、项目引用、DB 行数 |
| 成功支付 | 一笔正数 `amountMinor` 的成功实付，按成功日归期 | 纳入该 `tenantId + institutionId + currency` 的实付与净额 | pending、failed、cancelled |
| 确认退款 | 一笔正数 `amountMinor` 的确认退款，按确认日归期 | 纳入退款并从净额扣减；可产生负净额 | 退款申请、失败退款、未确认冲正 |
| 客户匹配 | 来源客户引用到已验证机构内客户稳定引用的结果 | 已匹配支付才可进入付费客户数/客单价；未匹配金额仍入机构金额 | 外部客户 ID、客户姓名或猜测匹配 |
| HIS 项目映射 | 来源项目引用或别名映射至当前机构、有效且版本化的 HIS 标准目录 | 已映射事实才进入标准项目排行、占比和详情 | ERP/POS/导入项目自身作为 canonical 项目 |

所有持久化事实都必须由服务端强制带入 `tenantId + institutionId`，不得由客户端、文件内容或 adapter 回传的 scope 覆盖。跨机构、跨 tenant 或来源所属范围不一致的记录 fail-closed，不能写入、合并、纠正或参与聚合。

## 三、拟纳入的逻辑记录与最小字段域

这是数据变更申请中的逻辑记录，不是表名、列名、SQL 或 ORM 定义。总协调台在获批 migration 时决定实际结构，同时必须保留以下语义和约束。

| 逻辑记录 | 必须承载的低敏字段域 | 关键约束与关系 |
| --- | --- | --- |
| 消费来源 | `tenantId`、`institutionId`、来源类型、来源安全引用、启用/停用状态、最近观测时间、来源高水位、安全审计引用 | 一个来源只作用于所属机构；高水位是已接受规范化事实的位置/时间/版本摘要，不是外部 payload |
| 导入批次 | 双 scope、预检安全引用、批准行数与摘要 digest、目录/映射版本、操作者安全引用、批准与审计引用、批次状态 | 只接受独立受控导入任务已批准的命令；批次不可被静默覆盖 |
| 导入批次行结果 | 批次安全引用、稳定行序号或安全行引用、规范化结果状态、低敏 failure code、事实/纠正安全引用 | 不保存原始文件行、PII、支付号、外部账号或自由文本；拒绝行不产生金额事实 |
| 稳定业务消费单 | 双 scope、机构内稳定安全引用、来源关联、可空客户匹配关联、可空 HIS 映射关联、可用性/冲突质量状态 | 同 scope/source 的同一稳定引用不可指向冲突归属；缺失时不阻断可靠金额，但禁止计数与明细能力 |
| 支付事实 | 双 scope、来源/批次关联、来源记录安全引用、修订、事件时间、接收时间、币种、正数 minor 金额、稳定消费单关联、归因质量 | 只允许 `payment_succeeded`；币种为 ISO 4217 三字母代码；金额为正安全整数 |
| 退款事实 | 双 scope、来源/批次关联、来源记录安全引用、修订、确认时间、接收时间、币种、正数 minor 金额、可空稳定消费单关联、归因质量 | 只允许 `refund_confirmed`；退款以正数存储、聚合时扣减；可空关联形成可见孤儿退款质量结果 |
| 客户匹配结果 | 双 scope、来源客户安全引用、状态、已验证 customer 安全引用或内部低敏候选引用、版本、复核审计引用 | 状态为 `matched`、`unmatched` 或 `pending_review`；候选不等同于已匹配，且不进入客户数 |
| HIS 项目映射结果 | 双 scope、来源项目安全引用、HIS 目录版本、映射状态、已确认标准项目安全引用或内部低敏候选引用、版本、复核审计引用 | 状态为 `mapped`、`unmapped` 或 `pending_review`；仅当前机构真实、隔离、可审计目录版本可承接 `mapped` |
| 事实身份与纠正链 | 双 scope、来源、来源记录安全引用、来源修订、事件类型、前序安全引用、纠正原因码、操作者与审计引用、有效性状态 | 身份至少由机构、来源、记录、修订和事件类型组成；纠正链必须完整且唯一，断链或分叉 fail-closed |

金额只按 `institutionId + currency` 分区保存和聚合；不得跨币种相加、换算或以默认币种补齐。`amountMinor` 不在本迁移中定义展示精度或舍入策略。

## 四、状态、归因与质量语义

### 4.1 支付、退款与归期

- 仅 `payment_succeeded` 计入成功实付，按成功日进入机构时区内的统计期间。
- 仅 `refund_confirmed` 计入确认退款，按确认日进入期间；其正数金额在净额中扣减，净额允许为负。
- `pending`、`failed`、`cancelled`、退款申请中和退款失败不计入金额；它们只能作为来源质量/覆盖统计，不能显示为金额 `0`。
- 可确认的孤儿退款仍按币种影响机构退款和净额，并标记质量异常；它不创建付费客户、不虚构消费单或项目归属。

### 4.2 客户、项目和稳定消费单

- `unmatched`、`pending_review` 客户的可靠支付/退款仍计入同币种机构金额；不进入付费客户数、客单价、客户结构或客户级消费结果。
- `unmapped`、`pending_review` 项目的可靠金额仍计入同币种机构总额与质量摘要；不进入 HIS 标准项目排行、占比或项目详情。
- 没有可靠稳定业务消费单引用时，只关闭消费单数/次数、明细列表和记录详情；可靠基础金额、趋势、项目金额、机会和后续报告输入不被该缺口阻断。
- 稳定消费单引用重复、冲突、与支付/退款归属不一致或无法落在同一机构/来源时，保留受控质量结果，不将未知解释为 `0` 或任意选择一方。

### 4.3 来源覆盖、高水位与过期

每个来源需保留可审计的最后成功观测、可比较的来源高水位、已接受/拒绝/冲突记录计数和质量摘要。高水位只能在一批规范化、幂等和纠正校验均成功提交后推进；部分行非法时，已接受合法事实可提交，但高水位和批次摘要必须明确 `partial` 覆盖及拒绝计数，不能伪称完整同步。来源过期、断连、拒绝或未发布不能把未知来源解释为零，也不能驱动当前写操作。

## 五、幂等、重放与追加纠正

### 5.1 幂等身份和冲突处理

每一支付或退款事实使用至少下列逻辑身份：

```text
tenantId + institutionId + source + sourceRecordReference + sourceRevision + eventType
```

- 同一身份且等价规范化内容是重放：只保留一次有效事实，并记录低敏重放统计。
- 同一身份而不可等价是冲突：不按输入数组顺序、修订字符串或最近接收时间猜测有效版本；记录受控冲突质量，等待来源或人工纠正。
- 身份中的 scope、来源、安全记录引用、修订、事件类型、事件时间、接收时间、币种和金额任一无法可信规范化时，该行被拒绝并留低敏原因；同批其他合法、独立事实仍可完成。
- 全批没有任何合法事实且存在输入失败时，批次为 rejected；混合合法/非法时为 partial。响应、审计与治理摘要均不得回显原始行、文件、订单/支付/退款号或外部 payload。

### 5.2 追加纠正链

纠正只能追加，不得原地覆盖或删除历史事实。新事实须以受控原因码、操作者安全引用和审计引用指向明确前序事实；链完整、单一且同 scope/来源/业务归属时，才可确定唯一有效事实。断链、循环、分叉、跨机构、跨来源或冲突归属的链 fail-closed：保留历史和质量异常，但不按数组顺序猜测“最新”。

有效事实切换必须与对应的高水位、批次摘要和审计写入同一原子边界；任何一项失败不得推进高水位或产生部分已生效纠正。

## 六、数据库约束、索引、删除和并发申请

总协调台在实际结构中应将以下作为 migration 验收项，而非由栏目 PR 自行实现：

| 类别 | 必须验证的约束 |
| --- | --- |
| 机构隔离 | 每个事实、批次、映射、匹配、消费单和纠正边都存双 scope；复合外键/查询条件不能只用 tenant 或单一全局 ID 连接 |
| 去重 | 事实身份复合唯一约束覆盖 `tenantId + institutionId + source + sourceRecordReference + sourceRevision + eventType`；并发写入产生同一结果，不重复计金额 |
| 归属 | 稳定消费单、客户匹配、HIS 映射、支付、退款和纠正前序只能落在同 scope；退款关联与支付/消费单币种不一致时拒绝或标记孤儿，不隐式换算 |
| 金额与币种 | minor 金额严格为正安全整数；币种限制为 ISO 4217 三字母代码；退款扣减只在查询/聚合语义发生 |
| 时间与版本 | 事件时间、接收时间、来源修订、目录/映射版本和来源高水位均可审计；不以服务器默认时区替代机构业务日期 |
| 删除与归档 | 已接受事实、批次、映射复核和纠正链不可硬删；业务失效、撤销或纠正均追加版本化状态与审计，不破坏可追溯性 |
| 并发 | 幂等、纠正有效性切换、批次状态、高水位推进和审计必须有事务/锁或等价并发控制；冲突不能静默 last-write-wins |

实际 migration 与写库测试只能使用独立测试数据库/隔离容器，或先取得总协调台全局 DB lease。不得在多个 Worktree 共用的开发数据库并行运行 migration、回填、写库集成测试或修改共享数据。

## 七、实施阶段申请：expand → backfill → enforce

本节仅申请未来 migration 的阶段性门禁；每一步仍需总协调台单独批准实际 schema、SQL、Drizzle 元数据和测试。

| 阶段 | 允许的数据变更目标 | 必须先通过的门禁 | 失败处理与中间态 |
| --- | --- | --- | --- |
| Expand | 增加不破坏现有运行的消费来源、批次/行、事实、归因、映射和纠正承载能力及必要索引 | `MIG-01` 至 `MIG-04` 已合并；独立 DB/lease 已确认；无 adapter/runtime 同捆 | 旧路径保持可运行；新结构为空或未发布时不显示推测金额 |
| Backfill | 仅从获准、可审计且能重放的既有规范化业务事实回填；逐来源、逐机构记录覆盖和高水位 | 每行通过 scope、幂等、币种、金额、事件、纠正链和归因校验；无真实事实不造数 | 非法/冲突/缺失行隔离并形成低敏质量摘要；可暂停并从已提交高水位继续 |
| Enforce | 在覆盖、重复、纠正、孤儿退款、客户/项目匹配、稳定消费单与性能阈值均验收后收紧非空/唯一/外键约束 | 回填报告、抽样审计、并发验证、回滚演练和总协调台签字完成 | 任一门禁不通过则不 enforce，维持 capability-off，不以默认值填洞 |

回填不会从治疗摘要、平台商业记录、演示数据或未获准外部来源推断支付、退款、客户、项目或消费单。HIS、ERP/POS 与受控导入的原始获取、解析、同步、重试、凭证与网络仍由串行外部集成任务负责。

## 八、审计、权限和隐私边界

- 所有批次批准、行级规范化结果、拒绝/冲突、映射或匹配复核、纠正、有效性切换和高水位推进都需记录操作者/服务安全引用、时间、原因码、前后版本/安全引用和 `tenantId + institutionId`；审计不可用时高风险写入 fail-closed。
- 持久化与治理输出只使用低敏安全引用和受控原因码。禁止存入或返回原始订单/支付/退款号、文件内容、客户姓名/联系方式、外部账号、凭证、自由文本、SQL、堆栈或 provider payload。
- 本申请不声明或复制 `InstitutionSourceEnvelopeV1`、`InstitutionOperatingContextV1`、`ControlledImportCommandV1` 或公共 readiness/failure-code 枚举。公共声明只归总协调台；独立受控导入任务生产和执行其已冻结的 15 字段命令，本线只验收规范化结果。
- 经营分析后续只允许 `tenant_admin`、`tenant_operator` 在服务端当前机构范围读取低敏经营结果；本迁移本身不新增 API、UI 或权限端点。

## 九、回滚、停止条件与验收

### 9.1 回滚原则

- Expand 阶段失败：停止新写入并回退应用对新结构的读取；不删除已审计历史。
- Backfill 阶段失败：停止该来源/机构的后续批次或高水位推进，保留已验证提交和低敏失败摘要；修复必须走追加纠正，不覆盖事实。
- Enforce 阶段失败：撤回尚未安全启用的强制约束或 capability，保留可读审计和原始有效链；不得通过删除批次、事实或纠正记录“恢复”。
- 任何外部 adapter、导入运行时、数据库租约或审计写入异常，都阻断下一阶段，不允许以页面、mock 或人工 SQL 绕过。

### 9.2 总协调台验收清单

- [ ] 确认 `MIG-05` 位于已合并的 `MIG-01 → MIG-04` 之后，且 `MIG-06` 未混入。
- [ ] 验证双 scope、复合唯一身份、追加纠正链、并发高水位推进和审计原子性。
- [ ] 覆盖成功支付、确认退款、失败/取消排除、部分/全额/孤儿退款、负净额、重放、同身份冲突、断链/分叉纠正。
- [ ] 覆盖 CNY/USD 等币种隔离、未匹配/待复核客户、未映射/待复核项目、无稳定消费单引用和跨机构 scope mismatch。
- [ ] 验证来源高水位、partial/rejected 批次、逐行低敏失败结果、停启/回滚和回填断点恢复；未知、缺失或过期绝不显示为 `0`。
- [ ] 验证没有真实、隔离、版本化和可审计的 HIS 标准项目目录时，项目标准排行/详情与统一发布门禁保持阻断；金额质量摘要仍如实保留。
- [ ] 确认外部 HIS/ERP/POS、受控导入 runtime、API/UI、snapshot/报告、AI/provider、schema 实施和 migration 执行均不在本 docs-only PR。

## 十、申请后的真实阻塞

1. 总协调台需确认 `MIG-01` 至 `MIG-04` 的合并状态、可消费的机构/客户基础及唯一 migration 槽位。
2. 总协调台需指定独立测试数据库/隔离容器，或发放本轮唯一 DB lease；未满足前不得开始 migration、回填或写库测试。
3. 总协调台需在串行外部集成队列分别批准 HIS 目录与消费、ERP/POS、受控文件导入的来源契约及运行时；本申请不授予任何外部连接权限。
4. 总协调台需批准实际 schema、索引、外键、保留期、性能阈值和逐阶段回滚演练，才可把本申请转化为 `MIG-05` 实施任务。
